# ADR-0002：MiniJinja 与受控模板数据函数

状态：MiniJinja 和函数取数能力已采纳；同步/异步桥接是待原型验证的工程方案。来源：用户提出主题通过模板函数获取数据，并建议 MiniJinja。

替代最初的 Tera 计划。选择 MiniJinja 的函数、参数和状态扩展模型，不以“Tera 不支持函数”或未经测量的性能优势作为理由。

保留两条路径：常用数据异步预取，函数 miss 时受控查询。另将清单声明预取作为对照方案；它简化渲染期 I/O，但会限制动态查询或增加声明语言设计。

代价：同步模板与异步数据库桥接、请求作用域、预算、取消和动态缓存依赖必须验证。声明式预取也仍需要查询失效和 CPU/输出预算，不能视为零成本方案。

实施门槛：在正式冻结主题 API 和缓存结构前完成原型，测量慢查询、取消、并发上限、上下文隔离和缓存失效。原型失败时调整桥接或 API，不默默取消用户的函数取数需求。

见 [主题与渲染](../themes-and-rendering.md)。

本轮细化：M0 原型与纯预取的 M1 内容闭环没有串行依赖，M0 只作为 M3 主题函数契约与相关缓存实现的门槛。原型位于仓库 spikes/template-bridge/ 的独立实验工程，不能成为生产 crate 的依赖；去留和转正按路线图的退出规则处理。

M0 原型结论（2026-09，`spikes/template-bridge`，17 项真实 PostgreSQL 集成测试）：**桥接方案可行**。多线程 Tokio runtime 上，同步渲染经 spawn_blocking 进入阻塞池，模板函数在阻塞线程内以 `Handle::block_on(timeout(剩余截止时间, 查询))` 驱动 sqlx 查询；不新建 runtime，不在异步执行线程 block_on。预算组合为：渲染截止时间（传播到每次宿主调用）、每页独立查询次数（默认 10）、函数调用次数（默认 64，缓存命中也计入）、fuel 与递归深度。fuel 需显式启用 minijinja `fuel` 特性，且只按 VM 指令计量、不限制宿主函数内部 I/O，后者必须由截止时间单独限制；输出大小无引擎原生上限，需宿主侧实现。渲染许可由阻塞任务持有到退出，客户端放弃不提前释放；饱和时有限等待后返回受控错误。请求隔离采用 per-request Environment 副本（模板共享、函数表写时复制，固定开销约 5µs）加闭包捕获不可变 RenderScope；实测 32 路并行渲染无状态串用，函数 miss 与纯预取吞吐相当（16.4k vs 16.0k 渲染/s @ 许可 16）。冻结正式主题函数 API 时，采纳「预算化函数取数 + 预取优先」的组合，函数错误统一为带类别的受控失败，不做无限排队或静默降级。测量环境、失败场景矩阵与遗留问题见原型 README。
