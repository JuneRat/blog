# ADR-0012：先收敛前端取数与错误处理，暂缓 Query

- 状态：部分被替代
- 记录日期：2026-09-23
- 关联决策：[ADR-0011：Ant Design](0011-admin-ui-library.md)、[ADR-0013：TanStack Query](0013-tanstack-query.md)
- 当前参考：[后台开发约定](../admin-development.md)、[管理 API](../admin-api.md)

## 背景

UI 迁移完成后，多个屏幕仍各自维护取数状态和错误文案。看似相同的错误函数实际有不同语义：管理操作的 403 需要权限提示，登录失败不能被解释为没有管理权限，部分屏幕还要按业务码提供具体处理动作。

列表失败行为也不一致：有的保留旧数据，有的清空为默认值。这些差异应由界面用途决定，而不是由复制了哪段代码决定。

当时已识别 TanStack Query 的缓存和去重收益，但一批测试把请求调用次数当作列表刷新契约。引入缓存需要先重新论证这些断言，超出了单次样板收敛的范围。

## 决策

先建立公共错误模块，提供通用 `messageOf` 与管理场景的 `permissionMessageOf` 两个明确入口。屏幕可先按业务码处理，再回落到公共文案；不把所有 403 都解释为同一种用户问题。

当时采用轻量 `useResource`，集中一次请求的状态和成功、失败收尾。失败后保留旧数据还是采用兜底值由调用方显式选择；触发请求的 `useEffect` 及其依赖留在屏幕内，不再抽象一套隐藏依赖的触发协议。

暂缓引入 Query，先完成独立、可验证的收敛。需要共享服务端状态、跨屏失效或自动重取时重新评估；届时应修改与缓存冲突的测试假设，而不是长期以旧断言限制架构。

## 考虑过的方案

- **与 UI 迁移同时更换数据层**：会同时改变交互组件和状态生命周期，增加定位回归的难度，因此拆开进行。
- **立即全量迁入 Query**：有跨屏缓存收益，但当时任务目标是收掉重复逻辑；需要单独承担测试语义和缓存失效设计的成本。
- **把 effect 依赖也藏进通用 hook**：减少表面代码，却引入新的依赖协议，触发条件反而更难检查。
- **用 Redux 或 Zustand 管理这些服务端数据**：仍需自行实现请求、缓存、失效和竞态处理，未解决主要问题。

## 后果与限制

公共错误文案与明确的失败行为可以独立于取数库保留。合并服务器响应、维护编辑基线或按资源分别收尾的屏幕，不应为了统一形状硬套简单 hook。

当时的 `useResource` 没有请求去重、跨屏缓存或过期响应保护，只减少一次取数的重复代码。它是阶段性实现，不能承担服务端状态管理的全部职责。
