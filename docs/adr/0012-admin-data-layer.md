# ADR-0012：前端取数层——先抽公共 hook，暂不引入 TanStack Query

记录日期：2026-09-23。

状态：**已被 [ADR-0013](0013-tanstack-query.md) 替代**（其「暂不引入 TanStack Query」的第 4 条决策不再有效；公共错误文案与失败口径集中的部分继续有效）。原来源：后台迁到 Ant Design v6 之后，用户要求评估并落地「抽公共 hook 收掉重复样板」，并明确是否引入 TanStack Query。相关记录见 [ADR-0011](0011-admin-ui-library.md) 与 [架构总览 §7](../architecture.md)。

## 背景

后台迁到 antd v6 时，取数层刻意一个字没动——[ADR-0011](0011-admin-ui-library.md) 的执行顺序是「先换 UI、保留现有 `load()`，测试跑绿，再单独做数据层」，一次只改一个变量。迁移完成后取数层的实际状况：

- **15 份 `messageOf` 抄在 15 个文件里，而且不是同一份**：管理界面遇到 403 加「没有权限：」前缀（10 份）；登录、角色目录与 `auth.tsx` 不加（3 份，登录失败说成「没有权限」是误导）；用户与角色屏、改密弹窗先按业务码分支再回落（2 份）。
- 每个屏自己写 `data`/`error` 这对状态与「清错误 → 成功写入 → 失败落兜底」的收尾，**失败时的界面取决于当初抄的是哪一份**：有的失败清空列表显示空态，有的保留旧数据。
- 全仓 `setBusy`/`setLoading`/`useState<string | null>` 这类状态声明 107 处。

同时评估过 TanStack Query：它能给请求去重、跨屏缓存、mutation 状态与失效重取，而编辑器的标签/分类/系列目录确实在两个编辑器里各拉一遍。

## 决策

1. **先抽两个模块，不引入新依赖**：
   - `src/apiError.ts`：`messageOf`（通用）与 `permissionMessageOf`（403 加「没有权限：」）两个入口。**有意做成两个函数而不是一个布尔开关**——调用点读起来就是它要的语义，也不会有人「顺手统一」成一种而改掉另一侧文案。15 份重复到此收口。
   - `src/resource.ts`：`useResource<T>()` 提供 `data`/`error`/`setError`/`run`，把「清错误 → 成功写入 → 失败按 `fallback` 落兜底并按 `messageFor` 转文案」集中一处。**只暴露 `setError` 不暴露 `setData`**：需要直接写数据的是「合并服务器响应/乐观更新」的屏，它们本来就要保留自己的状态，不适合套这个 hook。

   这一步的实测结果：`messageOf` 从 15 份收口到 1 个模块（2 个入口），另有 2 个屏级「按业务码分支」的映射器保留分支、回落共用 tail；`useResource` 被 6 个屏采用（标签、分类、系列、文章列表、页面列表、角色目录），取数样板从每屏 14 行降到 6–8 行，全部在**零测试改动**的前提下完成（19 个测试文件 / 138 条用例保持全绿，其中 10 条是为这两个新模块补的单测）。

2. **`useResource` 不接管 `useEffect`**。每个屏的触发条件不同（`page`、`revision`、权限开关、slug 变化），把依赖数组藏进 hook 就得再发明一个 `deps` 参数——那只是把显式的依赖列表换成更隐蔽的一处。触发仍写在调用点，hook 只负责状态与收尾。

3. **把「失败口径」变成显式参数**：`fallback` 不传表示失败保留已有数据（「操作成功但重载失败」不能把已生效的行抹掉），传 `[]` 表示落空态；`messageFor` 决定是否加权限前缀。差异从此是参数，不是「抄了哪一份」。

4. **暂不引入 TanStack Query**。决定性理由是**测试的语义成本**：现有用例里有相当一部分直接断言 `api.listXxx` 的**调用次数**（「失败时不再重载，`listPosts` 仍 ×1」「重载 `listTrash` ×2」）。Query 一旦缓存命中就不再发请求，这些断言全部要逐条重新论证而不是改数字——工作量与一次小迁移相当。而后台并发用户少、数据量小，收益主要是少写样板，我们刚用 `useResource` 拿到了这部分收益，代价是零新依赖、零测试改动。

5. **写明什么时候值得再回头换**：出现「同一份服务端数据被多个屏同时展示/需要自动失效」的真实需求（仪表盘、跨屏草稿列表、后台自动重取），或列表需要乐观更新时。届时迁移配套两件事：把「调用次数断言」改成以行为断言为主、次数断言只保留在真正要求去重/幂等的地方；以及把 Query 的 401 重试与 `version_conflict` 不可重试的语义和 `auth.tsx` 的 401 处理器接好。

## 被否方案

- **先做数据层、或与 UI 迁移同时做**：两个变量一起动，出问题无法 bisect；而且当时取数层几乎没有测试保护（现在有 128 条）。
- **把 `useEffect` 也收进 hook（带 `deps` 参数）**：见决策 2；把显式依赖换成隐蔽依赖，是新增 bug 类别而不是减少样板。
- **一次性全量上 Query**：在「没有缓存需求」的前提下，净收益只是样板，而样板已由 `useResource` 收掉；换来的是调用次数断言的全面返工。
- **Redux/Zustand 管服务端状态**：缓存失效、请求去重、竞态都得自己再写一遍，是经典错配。

## 代价与限制

- `useResource` 只收敛「一次取数」的形态。实际未采用它的屏各有具体原因，**没有硬套**：
  - 两个编辑器用 `Promise.all` 并发取标签/分类/系列三个目录；
  - 设置屏有两个资源（站点/主题）加冲突流程；
  - 媒体库一次取数要同时写 `items`/`total`/`page`，并另有资产详情；
  - 回收站需要额外的 `loading` 标志、失败时保留旧数据，还要做「当前页空则回退一页」；
  - 用户与角色屏同时管账号与角色目录；
  - 系列屏只迁移了外层「目录 + 错误」这一对，逐系列成员仍是自定义编排（失败时必须保留旧成员、只清展开键——无法用单个 `data`/`fallback` 对表达）。
- `run` 用「返回 `null`」表达失败，调用点要写 `if (result === null)`。列表/对象类型下不歧义；若将来 `T` 本身可为 `null`，需要改成判别联合。
- 仍然是手写取数：**没有请求去重、没有跨屏缓存、没有 stale-while-revalidate**。编辑器在两个屏各拉一次目录的重复请求依然存在。
- 「调用次数断言」的脆弱性没有消除，只是这一轮没去动它；换 Query 时它是第一笔要还的账。
- `useResource` 的 `run` 不做「过期请求丢弃」（不判断组件是否已卸载、也不比较请求序号）：这与迁移前的屏级实现一致，只是把原有行为集中起来，没有引入新的竞态保护。
