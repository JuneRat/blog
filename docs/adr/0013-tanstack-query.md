# ADR-0013：引入 TanStack Query

- 状态：已采纳
- 记录日期：2026-09-23
- 关联决策：[ADR-0012：公共取数与错误处理](0012-admin-data-layer.md)、[ADR-0014：后台稳定身份](0014-content-commits-and-stable-admin-identity.md)
- 当前参考：[后台开发约定](../admin-development.md#查询与缓存)、[管理 API](../admin-api.md)

## 背景

[ADR-0012](0012-admin-data-layer.md) 暂缓 Query 的主要顾虑，是缓存会改变请求次数，需要重新审视原有测试。用户随后明确接受 Query，并要求清理只固定内部机制的测试。

目录在编辑器与管理屏之间共享，写入后也需要跨屏更新。继续维护自研取数 hook，需要再次实现缓存、去重与失效；引入专门的服务端状态库更合适。

## 决策

采用 TanStack Query 5.x。每次 `AdminProviders` 挂载创建一个 `QueryClient`，避免模块级单例使不同应用实例或测试共享缓存。

集中默认策略：查询仅对 `ApiError` 的服务端故障重试，最多两次；写操作不自动重试。查询新鲜期为 30 秒，关闭窗口聚焦重取。401 仍由既有 API 与认证层处理，Query 不重试鉴权和版本冲突等业务失败。

当时的迁移范围是列表、目录、媒体、设置与文章编辑器目录。查询键集中定义，读路径交给 Query，写操作保留显式编排。Post/Page 详情与编辑基线继续由编辑器管理，不为了形式统一将服务器快照直接绑定到可编辑表单。

采用缓存同时承担失效责任：写入成功后更新或失效受影响的数据；分页变动检查整组查询；多步骤写入每一步成功后处理已经生效的部分。不能等“保存后发布”全部成功才让列表感知先行保存。

测试以用户可见结果为主。请求次数只用于确实要求去重、幂等或禁止调用的行为，不再用固定次数证明“列表刷新了”。保留取消确认不写入、重复提交受控、身份不匹配时拒绝保存等必要断言。

## 考虑过的方案

- **继续扩展 `useResource`**：需要自行补缓存、去重与失效，重复维护专门库已有的职责。
- **模块级 QueryClient 单例**：创建简单，但缓存生命周期不随应用实例结束，测试之间也容易相互影响。
- **同时把编辑器详情改为 Query**：响应回来时必须和当前输入、提交快照及基线合并，直接跟随查询数据会增加丢失未保存输入的风险，未纳入此次迁移。
- **保留所有调用次数断言**：会使测试绑定旧实现；改为验证界面行为，而不是为了维持断言放弃缓存。

## 后果与限制

共享查询减少重复请求，但切换页面不再保证立即访问服务端。集中查询键只能减少拼写错误，不能证明跨屏失效完整；每项写操作仍需按实际读取方验证。

后台重取不能无条件覆盖表单；发生冲突时，需要获取服务器当前值供用户决策，不能假设新鲜期内的缓存就是最新版本。Query 也不代替 `expected_version`、权限检查或编辑器输入合并。

## 后续变更

本记录替代 ADR-0012 的“暂缓 Query”决定；过渡 `useResource` 已移除，公共错误处理原则继续保留。

后续新增的评论模块使用局部查询键，评论开关使用 `useMutation` 和成功响应更新缓存；因此“键集中、写操作手写”描述的是当时迁移范围，并非所有后续模块已经统一的事实。当前覆盖、失效范围、表单约束和测试方法统一维护在[后台开发约定](../admin-development.md)，不在 ADR 中保存会随代码变化的失效矩阵。
