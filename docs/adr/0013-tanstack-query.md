# ADR-0013：引入 TanStack Query（替代 ADR-0012 的「暂不引入」决策）

记录日期：2026-09-23。

状态：已采纳并实现。来源：用户明确「TanStack Query 可以用」，并要求同时去掉不必要、过度防御的测试。本决策替代 [ADR-0012](0012-admin-data-layer.md) 的第 4 条（暂不引入），其余部分（公共错误文案、失败口径集中）继续有效。

## 背景

[ADR-0012](0012-admin-data-layer.md) 当时选择先抽 `apiError.ts` 与 `useResource`、暂不引入 Query，决定性理由是**测试的语义成本**：一批用例直接断言 `api.listXxx` 的调用次数，Query 一旦缓存命中就不再发请求，这些断言要逐条重新论证。

用户随后明确：Query 可以用，并且要**去掉不必要、过度防御的测试**——也就是把那笔成本直接结清，而不是为了保住「调用次数」这类内部机制断言而放弃缓存。于是两条决策一起做。

## 决策

1. **引入 `@tanstack/react-query` 5.x**，`QueryClient` 在 `AdminProviders` 里用 `useState` 惰性创建（每次挂载一个实例）。**不做模块级单例**：测试在同一文件内共享模块状态，模块级缓存会让用例之间互相污染——上一条取到的数据被下一条当成已有缓存，请求不再发出、断言莫名通过。

2. **重试策略写死在 client**：查询只重试服务端故障（`ApiError.status >= 500`，最多 2 次），业务错误码不重试——`version_conflict` 重试会掩盖真实的并发冲突，`forbidden`/`tag_in_use`/`not_found` 重试只是把提示推迟几秒。**写操作 `retry: false`**：服务端可能已经应用，重试可能造成重复写入。`refetchOnWindowFocus: false`（后台是少人用的管理界面，不靠窗口聚焦静默刷新）、`staleTime: 30s`。

3. **查询键集中在 `src/queryClient.ts` 的 `queryKeys`**：失效写错键是这类库最难发现的一类 bug，集中定义只是防拼错。

4. **读路径用 `useQuery`，写路径保留手写流程**。乐观锁 `expected_version`、409 的「重新加载／仍然覆盖」、`pickServer`/`mergeServer` 的飞行期间合并语义都是领域逻辑，不交给库；写成功后用 `invalidateQueries` 代替原来的「手写再拉一次」。

   随之而来的硬要求：**每个写路径都要显式失效它改动的那些键，包括跨屏的**。缓存 + 关闭窗口聚焦重取意味着「不失效就看不到更新」——这与手写 `load()` 时代「每次挂载都重取」的行为不同，是本库最容易漏的一处。当前的失效矩阵：

   | 写操作 | 必须失效 |
   |---|---|
   | 文章编辑器：创建/保存/仍然覆盖 | `posts()` |
   | 文章编辑器：发布/撤回 | `posts()`；**有未保存改动时是「先保存、再改状态」，先行保存成功后要立刻失效一次**，不能等状态切换成功——那一步失败时返回列表仍是保存前的数据（下面那次仍要保留：状态列只有切换成功才变） |
   | 页面编辑器：创建/保存/仍然覆盖/物理删除 | `pages()` |
   | 页面编辑器：发布/撤回 | 同文章编辑器（先行保存后立刻失效一次） |
   | 文章列表：移入回收站 | `posts()` + `trashAll()`（回收站多了一行） |
   | 回收站：恢复 | `trashAll()` + `posts()`（文章回到列表） |
   | 回收站：永久删除 | `trashAll()`（列表不受影响） |
   | 媒体库：上传/删除 | `media(...)`（`mediaUsage` 在被拒时一并失效） |
   | 标签/分类/系列/用户/角色/设置 | 各自目录键 |

   **一个写操作里有多次服务端调用时，每一次成功都要失效它改动的那部分**：先行保存改了标题/slug，发布只改状态；前者成功就该立刻反映到列表，否则「保存成功 + 发布失败」这条组合路径会留下旧数据。

5. **错误分两处展示**：`query.error` 是取数失败（经 `permissionMessageOf` 转文案），另有屏级 `actionError` 承接前端校验与写操作失败；展示时动作错误优先。这两类错误的来源与生命周期不同，混成一个 slot 会让「取数失败」和「刚刚操作失败」互相覆盖。

6. **删除自研 `useResource`（`src/resource.ts`）与其单测**。它只是迁移前的过渡形态：Query 的 `data`/`error`/`isPending`/`refetch` 覆盖了它的全部职责，且多提供了缓存与失效。留下两套并行机制只会让人分不清该用哪个。

7. **测试口径（本次的第二个决策）**：
   - **删除**只锁「内部重新取数机制」的断言——典型是 `expect(api.listX).toHaveBeenCalledTimes(2)`（用来证明「列表刷新了」）与 `expect(api.getPost).not.toHaveBeenCalled()`（用来证明「没有重载」）。它们描述的是实现怎么走，不是用户看到什么，而且正是它们把缓存挡在门外。
   - **替换**成界面结果断言：要证明「创建后列表刷新」就让 mock 第二次返回含新条目的数据、断言新条目出现；要证明「冲突后重载」就让第二次返回服务端当前值、断言它显示出来。
   - **保留**「不发请求本身就是需求」的断言：确认弹窗取消后不发写请求、无权限时不调接口、重复提交只发一次、以及 A→B 加载失败时拒绝写入。
   - 判定标准：**删掉这条断言后，如果功能坏了仍然会被别的断言抓住，它就是过度防御**；如果没有任何守卫，就换成行为断言而不是直接删。

8. **迁移范围**：文章/页面列表、回收站、标签、分类、系列、角色目录、媒体库、用户与角色、站点设置与主题设置，以及**文章编辑器的三个目录**（标签/分类/系列，与管理屏共用缓存，两个编辑器之间也不再各拉一遍）。**编辑器的详情加载**（`getPost`/`getPage`）仍留在屏内：它要按字段合并服务器响应、驱动 dirty 基线并与表单值同步，塞进 Query 的 data 流只会更绕；待那部分重构时再评估。

## 被否方案

- **保持自研 `useResource`**：缓存、去重、失效都要自己再写一遍；而「同一个目录被多个屏展示」的收益（两个编辑器 + 三个管理屏）拿不到。
- **模块级 `QueryClient` 单例**：见决策 1 的测试污染问题。
- **编辑器的详情也改成 `useQuery`**：`mergeServer` 需要「响应回来那一刻」的当前输入，`setFieldsValue` 与 dirty 基线也要跟着走；用 Query 的 data 流表达反而更绕，收益只是形式统一。
- **为了保住调用次数断言而不引入 Query**：那是让实现细节决定架构。用户已明确接受清理这批断言。

## 实现中踩到并固定的坑（写给下一个人）

1. **5xx 重试把「读取失败」推迟到重试耗尽**（1s + 2s ≈ 3s）才可见。错误态用例要用不重试的 4xx，否则 `findBy*` 默认 1s 超时；`mockRejectedValueOnce` 更会被第二次尝试「救活」成成功，错误态永远不出现。本次两条 500 的 fixture 因此改成 403/409，并在测试里注明原因。
2. **`invalidateQueries` 对非活跃查询只打 `isInvalidated` 标记**，不立刻发请求；下一次挂载时按 `isStaleByTime` 重取。「上传后回到第 1 页」正是依赖这一点。
3. **分页查询要按族失效**：页码在键里，只失效当前页会留下兄弟页的陈旧数据（总数与被删行都变了）。`queryKeys.trashAll()` 这类前缀键是必需品，不是可选优化。
4. **`isPending` 不等于空态**：`isPending` 只在「还没有任何 data」时为真，成功但空列表是 `isSuccess` + `data: []`；「有请求在飞（含后台重取）」要用 `isFetching`。另外 `enabled: false` 时 `isPending` 恒为 true，权限分支不能靠它渲染 spinner。
5. **翻页期间保留上一页内容**用 `placeholderData: keepPreviousData`（等价于旧实现里「重载不清空列表」）。代价是 `data` 会落后于请求，页面必须以 `data.page`（服务端回显）为准，`requested` 只用于组 key。
6. **表单屏不要把 `x.data` 无条件写回表单**：保存成功后的后台重取会吞掉「等待期间的新输入」。设置屏用的是「仅首次 apply + 本地基线」。
7. **冲突快照要绕开缓存**：冲突流程需要「此刻服务器上的值」，走 Query 会命中 `staleTime` 内的旧缓存——而冲突的另一方就是这份旧值。设置屏那两处保留直调 `settingsApi.get()`，这是刻意例外。
8. **mock resolve 之后 DOM 不会同步更新**（`notifyManager` 批处理），紧跟 `toHaveBeenCalled` 的同步 `getByText` 不可靠，用 `findBy*`。
9. **「写后看不到更新」这类回归，测试必须先把缓存落地**：正确形态是「先访问列表（让缓存成立）→ 进入编辑器改并保存 → 返回列表 → 断言新值」。只在编辑器与列表之间来回、或渲染时就返回新数据的测试**测不出问题**（没有旧缓存可命中），会给出虚假的安全感。`tests/editor.test.tsx` 与 `tests/listScreens.test.tsx` 里各有这类用例，且都在去掉失效后验证过会变红。

## 代价与限制

- 缓存意味着「切换屏幕不再总是重新取数」：排查「界面没更新」时先看 `staleTime` 与写后是否 `invalidate` 了正确的键。
- 键集中在 `queryKeys` 只能防拼错，**防不了漏写 invalidation**——新增写操作时漏掉失效，界面就会停在旧数据上，这类 bug 需要靠测试的行为断言兜住（这也是决策 7 要求写行为断言的原因）。
- 新写测试**不要**再用 `toHaveBeenCalledTimes` 表达「刷新了」：缓存命中会让它时灵时不灵。
- Query 的错误重试与 `auth.tsx` 的 401 处理目前是两条独立路径：401 仍由 `api.ts` 的全局未授权处理器负责（清 token、跳登录），Query 侧只是不重试。若将来要在 Query 层统一处理鉴权失败，需要把两者接在一起。
