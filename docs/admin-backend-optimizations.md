# 后台管理系统需后端配合的优化规划

本文档记录了后台前端（`apps/admin`）完成纯前端优化后，针对当前系统瓶颈识别出的**需后端（Rust 服务端与数据库）配合改造的优化项**。涵盖架构设计、API 契约、数据模型及落地优先级。

---

## 一、背景与现状

在第一阶段（纯前端改造）中，后台已完成了如下能力的落地：
- 支持浅色 / 暗黑 / 跟随系统主题切换；
- Markdown 编辑器集成实时字数、阅读预估时间统计及全屏沉浸式写作模式；
- 独立页面与导航项的 Slug 自动联想补全；
- 评论管理的前端多选与并发批量审核；
- 标签选择器滚动优化与 Ant Design 组件规范对齐。

受限于当前后端 API 契约与数据库模型，部分深水区体验（如高并发一致性、版本恢复、协作冲突、大图性能和实时状态）仍存在瓶颈，亟需后端协同推进。

---

## 二、优化项目清单与详细方案

### 1. 核心内容与编辑协作

#### 1.1 原生事务性批量操作接口（已实现）
- `POST /api/admin/v1/posts/batch` 支持 trash/restore/purge/change_status/change_category。
- `POST /api/admin/v1/comments/batch` 支持 approve/spam/trash/restore/pending；恢复回到待审核，保留回复关系。
- 入参统一使用 `items:[{id,expected_version}]`，最多 100 项；参数使用明确的状态/分类结构，避免裸 ID 或任意 params 绕过版本与领域规则。
- 全部目标的当前归属、权限、版本和转换在一次数据库事务内核验；任一失败整批回滚（含关联清理与审计）。实际变化只追加一条聚合审计，全部无变化时不写入。
- 评论单条物理删除未纳入批量审核，仍遵循不可变回复链与公开占位语义；文章永久删除时清理整棵评论树。
- 前端已接入文章列表、回收站和评论管理；成功后刷新相关缓存，失败后清空选择并刷新。遇到 409 时核对新列表后重新选择，不自动重放。详细输入/返回类型见[批量 API 契约](admin-api.md#文章与评论批量操作)。

#### 1.2 文章历史版本快照与 Diff 对比（Post Revisions & Rollback）
- **当前现状**：
  - 目前仅靠实体上的 `version: i64` 乐观锁防并发覆写，但数据库未持久化修改历史。一旦发布或保存了错误内容，无法追溯旧版或一键还原。
- **后端改造方案**：
  - 新增 `post_revisions` 表（字段：`id`, `post_id`, `version`, `author_id`, `title`, `content_snapshot`, `created_at`）。
  - 在每次编辑保存成功后（或由作者主动勾选“生成版本快照”），异步写入快照表。
  - 新增接口：
    - `GET /api/admin/v1/posts/{id}/revisions`：获取文章版本历史列表。
    - `GET /api/admin/v1/posts/{id}/revisions/{version}`：获取指定版本的完整正文与元数据。
    - `POST /api/admin/v1/posts/{id}/rollback`：以指定版本内容生成新的递增版本覆写当前文章。
- **收益**：前端编辑器侧边栏可展示“修订历史”，支持类似 Git 的双栏 Diff 对比与一键还原。

#### 1.3 编辑协作锁与在线防冲突（Heartbeat / Presence Lock）
- **当前现状**：
  - 依赖保存时的 `expected_version` 乐观锁。当两位管理员同时打开编辑同一篇文章时，后保存者将触发 409 `version_conflict` 错误，导致编辑内容覆盖或丢失。
- **后端改造方案**：
  - 基于内存/Redis 或数据库租约机制提供心跳锁：
    - `POST /api/admin/v1/posts/{id}/lock`：进入编辑页获取锁（TTL 30~60 秒）。
    - `PUT /api/admin/v1/posts/{id}/lock`：前端每 20 秒发送心跳续约。
    - `DELETE /api/admin/v1/posts/{id}/lock`：离开或保存时释放。
  - 获取失败时返回持锁人信息（`{ locked_by: "Alice", locked_at: "..." }`）。
- **收益**：后来者打开时即明确提示“用户 Alice 正在编辑此文章”，自动降级为只读预览，从根源避免内容冲突。

#### 1.4 管理端原生评论回复接口（Admin Direct Reply）
- **当前现状**：
  - 后台“回复评论”调用的是前台公开的 `/api/v1/posts/{slug}/comments` 接口。若前台开启了 Turnstile 验证码、触发了访客限流或文章设置了评论关闭，管理员回复便会直接失败，且无法直接赋予官方“作者”身份。
- **后端改造方案**：
  - 新增专用接口 `POST /api/admin/v1/comments/{id}/reply`：
    - 走后台会话权限鉴权，跳过前台验证码与访客频控校验；
    - 自动以管理员身份创建回复，状态直接置为 `approved`；
    - 标记 `is_author = true` 或记录 `admin_user_id`。
- **收益**：后台回复与前台访客评论解耦，彻底避免风控和验证码阻断。

### 2. 媒体库性能与资产管理

#### 2.1 自动生成 WebP 缩略图与多尺寸支持（Thumbnails）
- **当前现状**：
  - 上传只存原始二进制文件，媒体库网格和文章封面选择器中直接加载原图（单图可达 10MB+），网格加载卡顿严重且消耗大量带宽。
- **后端改造方案**：
  - 在媒体存储阶段，使用 `image` / `webp` crate 自动生成小尺寸缩略图（如宽度 320px WebP）与中等尺寸图片。
  - `MediaAsset` 响应结构中增加 `thumbnail_url` 和 `variants` 字段。
- **收益**：媒体库首屏加载加速 5~10 倍，大幅削减服务器出口带宽。

#### 2.2 媒体分组与未引用孤儿资源清理（Folders & Orphan Cleanup）
- **当前现状**：
  - 媒体库全平铺展示，无法按文件夹或主题组织；无法识别哪些图片已无任何文章引用。
- **后端改造方案**：
  - 数据库 `media` 表增加 `folder` 或标签关联。
  - 新增 `GET /api/admin/v1/media/unused`：扫描全文未引用的孤儿媒体。
  - 新增 `DELETE /api/admin/v1/media/batch`：批量硬清理废弃资源。
- **收益**：媒体资产结构清晰，并可定期清理无用文件释放磁盘。

### 3. 实时通信与可观测性

#### 3.1 基于 SSE 的长连接事件与任务推送（Server-Sent Events）
- **当前现状**：
  - 任务中心（静态重建 `html_rebuild`、保留期清理 `retention`）依赖前端 2秒/10秒 短轮询，存在无效请求与展示延迟。
- **后端改造方案**：
  - 提供单向流端点 `GET /api/admin/v1/events`（Axum SSE）：
    - 任务状态变更推送：`task.progress`、`task.finished`；
    - 审核通知推送：`comment.new`。
- **收益**：彻底取消定时轮询；任务进度条秒级平滑刷新，顶栏即时显示新待审红点。

#### 3.2 外部统计插件与可选报表接入（Analytics Plugins）
- **当前现状**：
  - 已提供默认关闭的 `analytics-umami` 插件，配置脚本地址、站点 ID 和可选报表地址后，在公开页面采集访问数据；后台插件卡片提供“查看统计”链接。采集与报表由 Umami Cloud 或自托管 Umami 提供，博客不存储访问明细。使用方式见[插件机制](plugins.md#umami-访问统计)。
  - 后台尚无内置统计看板和外部报表查询 API。
- **后续候选方案**：
  - 文章总数、草稿数、待审评论数直接由主库聚合，与访问统计分开。
  - 需要后台访问趋势、来源和热门文章时，增加服务端 Umami 报表适配器，凭据保留在服务端，提供统一查询 DTO、短期缓存、超时和不可用状态。
  - 不同服务的 PV/UV、时区、机器人过滤和数据延迟须明确；列表按阅读量排序另需本地读模型，不由脚本接入自动获得。
- **收益**：按需开启统计，复用外部服务的分析与报表能力；后续再按实际需求接入后台看板。

### 4. 规范对齐与安全加固

#### 4.1 用户与后台评论列表分页契约对齐（已实现）
- **实现结果**：
  - `/api/admin/v1/users?page=1&per_page=50` 返回标准分页契约，总数与条目从同一数据库快照读取，含软删除账号；默认每页 50 条，最多 200 条，非法分页参数拒绝。
  - 用户页面显示总数并支持页码选择、直接跳页和失效页回退，不再多读取一条；最后可登录 Admin 的判断仍使用全站计数。
  - 后台评论补齐 `page/per_page`，保留额外的 `enabled` 并返回实际全站评论开关；固定每页 20 条，公开评论契约保持原有形式。
  - 用户列表 DTO：
    ```rust
    pub struct UserPage {
        pub items: Vec<AdminUser>,
        pub total: i64,
        pub page: i64,
        pub per_page: i64,
    }
    ```
- **收益**：文章、页面、媒体、用户与后台评论共用分页字段；目录数组和审计游标保留各自契约。

#### 4.2 双因子认证（2FA / TOTP）与多端活跃会话管理
- **当前现状**：
  - 仅支持单层密码与外部 OAuth；无法查看当前账号在其他设备上的登录态，密码泄露后无法远程注销。
- **后端改造方案**：
  - 提供 TOTP 密钥生成（二维码 URI）、绑定核验、登录第二步校验接口；
  - 提供 `GET /api/admin/v1/me/sessions` 与 `DELETE /api/admin/v1/me/sessions/{id}`（强制下线指定设备或一键下线其他所有设备）。
- **收益**：个人中心增加安全中心模块，极大提升管理后台的企业级安全性。

## 三、落地优先级与排期建议

| 阶段 | 优化项 | 改动难度 | 涉及范围 | 收益重点 |
| :--- | :--- | :--- | :--- | :--- |
| **已完成** | **原生批量操作接口与前端接入**（文章+评论） | 🟢 较低 | 有界版本输入 + 单事务存储端口 + 聚合审计 + 批量操作控件 | 原子批量提交，关联清理与审计失败一并回滚 |
| **已完成** | **用户与后台评论列表分页契约对齐** | 🟢 很低 | 同快照总数查询 + 契约导出 + 标准分页器 | 用户支持总数和跳页，评论保留 `enabled` |
| **P1（建议优先）** | **管理端原生回复评论接口** | 🟢 较低 | Axum 路由 + 评论状态写入用例 | 彻底解决管理回复时的限流/风控冲突 |
| **P2（中期推进）** | **图片缩略图自动生成** | 🟡 中等 | 媒体上传流水线 + `image` crate | 彻底解决媒体库加载卡顿与带宽消耗 |
| **P2（中期推进）** | **文章历史版本与快照 Diff** | 🟡 中等 | 新增 `post_revisions` 迁移表与用例 | 文章防误改、随时可找回 |
| **P3（体系完善）** | **编辑防冲突锁机制** | 🔴 较高 | 租约存储（Redis/内存）+ 续期接口 | 多人协同防内容踩踏 |
| **P3（体系完善）** | **SSE 实时推送通道** | 🟡 中等 | Axum SSE + 任务事件广播 | 消除轮询，提升实时感知体验 |
| **P3（体系完善）** | **双因子认证（2FA）与会话管理** | 🔴 较高 | 会话表扩展 + TOTP 算法接入 | 系统企业级安全加固 |
