# 数据库迁移与版本演进

## 保留已执行的基线

`migrations/postgres/0001_initial_schema.sql` 保留原始字节，不拆分、不重排，也不修改注释。SQLx 在 `_sqlx_migrations` 中保存版本与 SHA-384 校验和；改写已经执行的文件会使已有库无法通过校验。后续变化新增 `0002_<description>.sql`、`0003_<description>.sql`，按变更目的拆分；空库按顺序执行全部迁移，已有库只执行新增部分。

当前只支持正整数版本的前向 SQL 迁移，文件名使用小写字母、数字和下划线，如 `0002_add_post_summary.sql`。版本不可重复，不能插入旧版本、删除历史文件或复用版本号。SQLx 为每个迁移建立事务；需要非事务 DDL、分区、序列或复杂数据回填时，先补充对应的安装、授权与恢复支持及演练。

这里的可升级基线是现有 `0001_initial_schema.sql`，不是已删除的旧 `0001_identity_rbac.sql` 至 `0009_comments.sql` 链。旧链仍需显式迁移数据到新库，不能直接启动覆盖。

## 单一结构来源与共享清单

| 文件 | 职责 |
|---|---|
| `migrations/postgres/*.sql` | 唯一可执行的结构演进来源；已有文件不可变 |
| `migrations/postgres/schema.json` | 本版本的迁移校验和、完整表集合、逐表运行及维护权限 |
| `scripts/database-roles.sql` | 从清单与通用模板生成的授权脚本 |
| `docs/sql/postgres-core.sql` | 从迁移链生成的空库 DDL 参考，不作为部署入口 |

Rust 的迁移加载和安装续跑、Python 备份恢复共同读取迁移目录内的 `schema.json`，不再各自维护固定表数。任何本版本之外的表、迁移版本或校验和仍会被拒绝。运行目录必须包含 SQL 文件与清单；Compose 镜像已成套打包并使用绝对路径。

`schema.json` 的 `format: 1` 表示清单格式，`id` 表示结构契约身份，备份的 `format: 2` 表示备份布局，三者相互独立。相同 `id` 不代表不同迁移链可以互相恢复：核验仍要求全部迁移版本与校验和一致。旧备份须用匹配版本恢复再升级；新增表或迁移无需仅因此改变备份格式。

## 开发一次结构变更

1. 新增迁移文件，写明新增、修改或删除的结构及必要数据处理；不要编辑旧文件。
2. 更新 `schema.json`：新增表必须声明 `app` 和 `maintenance` 两组权限，无权限写 `[]`；删除表或修改列级权限也在这里更新。变化涉及业务引用或恢复校验时，同时修改相应业务规则。
3. 更新契约 `id`，运行生成器。它只追加新迁移校验和；已有迁移不匹配时直接报错。

```sh
python3 -B scripts/schema_contract.py --write
python3 -B scripts/schema_contract.py
```

4. 提交新增 SQL、清单和生成文件。不要手改授权 SQL 或 DDL 参考。通用授权规则在 `scripts/sql/database-roles.sql.in` 中维护。
5. 在临时 PostgreSQL 中验证空库安装、带数据升级、有效权限、备份恢复，以及受影响业务的数据不变量。特别是删除或重命名媒体、身份等核心结构，不能只修改表清单。

CI 对比 PR 基线（push 对比前一提交），阻止修改或删除旧 SQL；检查清单与生成文件一致性；在真实 PostgreSQL 上核对全部表和表级、列级有效权限。额外演练在临时目录追加一张测试表，验证已有数据升级、漏授权失败、旧备份按旧版本恢复再升级、新备份往返，以及安装中断后的续跑和非空表保护。测试不会向正式迁移目录添加业务表。

本地检查使用 `scripts/check.sh`；可用 `SCHEMA_BASE_REF=<完整提交 SHA>` 指定历史基线。真实恢复演练见[运维文档](operations-and-recovery.md#验证与部署证据)。

## 部署与恢复顺序

默认升级：用旧版本工具备份并核验 → 保存旧镜像、匹配的迁移清单/恢复工具与配置秘密 → 停止全部旧版本写入 → 启动新版本，由本站结构所有者账号自动迁移 → 验证新服务后开放流量。迁移失败时服务退出，不接受 HTTP 请求。无需额外账号或授权脚本，仍可显式执行 `blog migrate`。Compose 命令见[部署指南](docker-compose.md#升级维护与备份边界)。

可选分离账号模式下，受限运行账号只能核对迁移历史；须在停写期间先以结构管理账号执行 `blog migrate`，再执行新版本生成的授权脚本，最后启动运行账号的服务。

跨版本恢复必须分阶段：

1. 使用与备份匹配的应用、迁移目录和恢复工具，在新的隔离数据库完成 `verify`、`restore` 及业务核验。新版本工具拒绝旧迁移链的备份是预期保护，不能手改清单或 SQLx 历史绕过。
2. 停止核验服务，保持公开流量及全部写入关闭，用旧版本工具执行 `release`。它重新核验旧结构并撤销会话，只解除数据库标记，不启动服务或恢复流量。
3. 保持停写，切换新版本完成迁移（默认由启动执行；分离模式显式迁移并授权），完成升级核验，再开放服务。恢复核验模式只核对结构，即使使用结构所有者也不自动迁移。不要先升级数据库再调用旧工具 `release`，旧结构核验会失败。

升级失败时保持停写，先查明迁移事务和结构状态。不能把切回旧镜像视为数据库回滚；需要回退时用升级前备份恢复到新库，并配套旧镜像和旧工具。涉及跨迁移的数据转换或外部副作用时，另行定义回退步骤。
