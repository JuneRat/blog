# 备份与恢复

状态：13 表核心、当前主题目录与环境变量秘密引用的维护备份工具及本机隔离恢复演练已交付；生产维护编排、备份频率/保留期、RPO/RTO 仍待部署规格确定。下文媒体、队列等流程仅在对应功能交付后适用。采用单站点、PostgreSQL、维护窗口恢复，不承诺在线一致备份、零数据丢失或跨库无停机切换。

本文统一定义备份与恢复的操作边界，不重复内容保留、账号恢复和事件协议。相关规则见 [内容生命周期](content-lifecycle.md)、[身份与后台](identity-and-admin.md)、[扩展与数据](extensions-and-data.md)；方案取舍见 [ADR-0005](adr/0005-consistent-backup-and-recovery.md)。

## 1. 恢复单元与清单

数据库导出成功不等于站点可恢复。一次可用备份由同一 backup_id 关联下列材料，清单记录版本、数量、大小和校验和，包含完成标记：

| 材料 | 必须覆盖的内容 |
|---|---|
| PostgreSQL 一致性快照 | 当前 13 表：身份/OAuth、权限关系、文章/页面、分类树、系列顺序、标签关系与 settings；后续新增的媒体、审计、outbox 和任务也纳入同一恢复单元 |
| 本站静态资源/后续媒体对象 | 当前自托管 avatar/cover/logo 文件；未来媒体库的有效引用原件及必要派生文件，包括私有和回收站附件。外部 URL 对象不由本站备份保证恢复 |
| 主题 | 激活版本及仍被配置/历史激活记录要求保留的主题包、清单、设置和指纹资源 |
| 部署描述 | 应用构建标识、schema/导出格式版本、处理器版本、后台 SPA 的构建标识（git commit + 构建时间戳），以及恢复所需的非敏感配置及存储映射 |
| 秘密恢复材料 | secret 引用对应的安全存储备份、解密所需密钥版本和恢复方法；秘密材料独立加密保存、独立控制访问，普通清单只记录引用与版本 |

页面缓存、请求缓存和外部搜索索引按派生数据重建，不作为唯一事实来源。外部统计服务的数据保留由提供商策略决定，本站备份不承诺恢复第三方历史报表。逻辑导入导出服务于迁移，不替代此恢复单元。

后台 SPA 的 `apps/admin/dist` 属于源码 + lockfile 的可重建产物，**不进备份材料**；恢复流程按部署描述记录的构建标识（git commit + 构建时间戳）重建 dist，避免出现「数据库恢复了但前端版本与 API 不匹配」。

备份含私有内容和身份数据，必须限制访问并保护传输与存储；不能放在公开资源目录或可公开下载的对象前缀。本版无线上修订，整站备份不等于逐篇历史恢复；线上永久删除也不代表既有备份立刻清除，需明确备份到期规则。

## 2. 首期一致备份流程

1. 获取部署级维护互斥，阻止新业务写入，包括管理 API、上传、CLI、定时任务、主题激活及所有 worker；不能只禁用后台按钮。等待在途数据库事务、文件写入及外部投递退出或记录可核对结果。无法确认静止状态时终止本次备份，不写完成标记。
2. 停止会修改主库或对象的服务进程，保持维护页；暂停已交付的主题包回收、媒体删除、孤儿清理等任务。若有外部上传入口和有效上传授权，也必须停止写入或等到失效。记录维护开始时间和恢复所需的应用/schema 版本。
3. 在保持静止的窗口内导出数据库，按媒体/主题清单复制对象，并保存版本匹配的秘密恢复材料。数据库与对象存储不需要跨系统事务，但从生成清单到完成对象复制之间不得再修改或删除这些对象。
4. 校验清单、对象存在性、大小、校验和及秘密材料可用性。PendingDeletion 对象若已不存在，只有在确认无保留/公开引用且状态符合幂等删除规则时才可记为预期缺失；有效引用指向的对象缺失使备份失败。Staged 上传在清单中标记为未完成，恢复时不冒充 Ready。
5. 所有组成部分验证成功后写入完成标记，再解除维护并恢复服务。失败备份标记为不完整，保留上一份可用备份；只在恢复原部署状态确认安全后解除维护。

备份工具必须有失败清理与维护状态检查，不能因脚本异常让 worker 提前启动。在线备份或对象版本快照可以作为后续优化，但须先证明得到同等一致性，不能分别取两个任意时点的数据拼成完整备份。

## 3. 隔离恢复与重新开放

1. 停止或隔离旧部署，防止两个服务同时处理写入或投递。先在隔离环境恢复，默认关闭公开入口、外部投递和所有清理 worker；恢复模式由部署控制，不依赖可能已经回退的数据库开关。
2. 验证备份完成标记和清单，使用匹配的应用/schema 版本恢复数据库、媒体、主题和秘密材料。升级与恢复分开验证，不在恢复过程中盲目运行不兼容迁移。缺失必要密钥、有效引用对象或活动主题时保持隔离并报错。
3. 校验 slug 唯一及 Page 系统路由、分类树、系列位置、标签关系、公开条件、有效 Owner、settings/主题兼容性及秘密引用。媒体功能已交付时再核验资产状态和引用；Staged 上传转入补偿，PendingDeletion 在恢复删除前重新检查引用。
4. 当前会话和登录尝试只在进程内，停止旧进程并重建空存储，不能复用旧运行状态。本地密码失败限流同样只在进程内，恢复后从零计数；恢复不还原这些运行态。以后若加入持久会话、邀请或初始化凭据，恢复时一并撤销，防止备份回退使旧凭据重新有效。操作者核对 Owner、角色、settings.oauth、各账号是否启用本地密码与秘密引用，必要时执行带运维日志的离线账号恢复，不开放公开初始化入口。
5. 丢弃旧缓存并建立新的缓存命名空间，不能复用可能与备份外状态碰撞的 generation。事件系统如已接入，为新产生的事件建立新的 stream_epoch，避免恢复后重复使用旧版本序列；保留旧事件的原始身份和世代。搜索从恢复主库构建新索引命名空间及消费水位，完成校验后再切换；旧索引水位可能高于恢复库，不能直接接着消费旧命名空间。
6. 按下一节分类核对队列，验证登录、读取、编辑、发布、草稿隔离和媒体访问。完成恢复检查与记录后，再逐项开放写入、worker 和外部投递。演练环境始终禁止向生产接收端投递。

## 4. 恢复后的任务策略

| 任务 | 恢复策略 |
|---|---|
| 搜索同步 | 在新索引中从当前主库重建并建立匹配水位，切换前保持写入暂停；重新开放后只向新索引消费 |
| 媒体/主题清理（交付后） | 重新核验当前引用、保留期与状态，恢复租约并验证幂等后启动 |
| Webhook、业务通知 | 默认隔离恢复出的投递记录；核对外部回执后决定跳过或重放并审计。维护内容状态的接收端先确认新的事件世代与基线，再开放新投递 |
| 非关键访问统计 | 不批量回放旧访问事件，防止重复计数；按提供商契约恢复新采集 |

外部接收端可能已经处理了备份之后的事件，而恢复库中没有这次成功记录。重放必须沿用原 event_id，接收端去重仍是必要条件；确认跳过、继续核对和重放都是显式状态，不能伪造为投递成功。恢复点之后丢失的本地事件也无法仅凭备份补回，不承诺数据库回滚等于外部副作用回滚。

租约重置只能在旧 worker 已停止且外部在途请求已核对后进行。仅等待本地租约过期不能证明远端请求停止；结果不明的外部任务继续隔离。恢复边界和重放记录作为新的运维审计保存。

## 5. 交付与验收

当前工具为 [`scripts/recovery.py`](../scripts/recovery.py)。它要求操作者先在部署层停止服务、CLI 写入和 worker，再显式传入 `--maintenance-confirmed`；脚本不能凭自身证明所有外部写入已停止。备份用 `pg_dump` custom 格式，连同主题（含 `theme.json`；可用 `--resource name=目录` 附加当前自托管资源）写入权限为 0700 的临时目录；文件逐一记 SHA-256/大小，校验 `pg_restore --list`，最后才原子写出带 `COMPLETE` 的目录。OAuth `secret_ref` 会从数据库读取并记录引用名，实际秘密值不入备份；环境中缺少引用值时备份失败。应由独立的秘密管理备份保证相同版本可重建，不能把演练用占位值当生产秘密。

本机容器示例（`DATABASE_URL` 和秘密环境变量由受保护的 shell/部署环境注入，不写在命令行参数中）：

```sh
python3 -B scripts/recovery.py backup --output /secure/backups/blog-2026-09-23 \
  --theme-dir themes/default --docker-container blog-postgres --maintenance-confirmed
python3 -B scripts/recovery.py verify /secure/backups/blog-2026-09-23
python3 -B scripts/recovery.py restore /secure/backups/blog-2026-09-23 \
  --target-db blog_restore_drill_20260923 --output /secure/isolated/blog-2026-09-23 \
  --docker-container blog-postgres --isolation-confirmed
```

不使用容器时需在执行环境提供匹配版本的 `pg_dump`、`pg_restore`、`psql`、`createdb` 与 `DATABASE_URL`。恢复只允许新建 `blog_restore_*` 数据库，拒绝已有目标和原库，输出目录保留 `ISOLATED` 标记，不启动服务或 worker。它复核 13 表、迁移版本、可登录 Owner 和备份时记录的内容计数；缺秘密、损坏文件或校验失败均不得转为可用部署。若在创建隔离库后失败，保留 `FAILED` 标记供检查，操作者确认后手工清理隔离库。

2026-09-23 本机演练：从隔离源库备份，再恢复到新的 `blog_restore_roundtrip_v2`，一并恢复第二主题 `paper` 与其 API 版本清单；复核 6 用户、4 Post（公开/私密/草稿/回收站各 1）、1 Page、1 分类、1 系列、1 标签和 2 条 post_tags、1 位可登录 Owner，逐条核对正文、回收站状态/系列位置及标签关系。缺 `IDP_SECRET` 的恢复在建库前拒绝。该演练验证工具与当前 schema；生产 RPO/RTO 和外部秘密备份仍需另验。

M3 交付核心数据库/资源清单、维护备份、隔离恢复和身份核对；M4 加入媒体、搜索/Webhook 时补齐对应恢复流程；M5 对拟上线的全部能力执行完整演练。按实际交付范围验收：

- 备份期间尝试上传、发布及对象删除，验证写入被阻止；强制中断备份，验证不产生可用完成标记。
- 在空环境恢复公开/私有文章、草稿、Page、Post 回收站、分类树、系列顺序、权限和 settings；校验自托管资源与主题。媒体库交付后另验证共享附件和私有访问边界。
- 模拟对象、主题或密钥缺失，恢复保持隔离并明确报告缺失项；验证旧会话、邀请、登录尝试、本地密码失败计数及后续可能引入的初始化凭据不恢复有效。
- 模拟外部已投递成功但备份中仍为待投递，确认恢复不会自动重复发送，受控重放保持事件 ID。
- 对恢复前较新的搜索索引和缓存执行命名空间重建，确认恢复后的撤回、发布及媒体引用变化按新状态生效；验证新事件世代内相同数值版本可正常消费，旧世代迟到请求不会覆盖新状态。
- 记录备份大小、维护时长、恢复耗时和实际可恢复时间点，与部署前确定的 RPO/RTO 比较；未达到目标不能标记恢复验收通过。

## 6. 凭据泄露处置（本地密码）

适用于 `users.password_hash` 泄露、口令明文疑似泄露、或某账号被判定为已失陷。契约与参数见 [身份与后台 §7](identity-and-admin.md)，取舍见 [ADR-0009](adr/0009-local-password-authentication.md)。

处置目标是让**旧口令与旧会话同时失效**，不是在原地修补：

1. **定级与定界**。确认泄露材料是 Argon2id 哈希还是明文、涉及哪些账号、来源是数据库导出、日志还是第三方。哈希本身不等于明文（内存硬 KDF 使离线爆破昂贵），但一律按已泄露处理并轮换。
2. **止血：下发新口令**。对每个受影响账号执行 `blog user passwd --user <用户名>`（交互隐藏输入，或 `--password-stdin`）。该操作会写入新 Argon2id 哈希、递增 `users.version` 并撤销该账号全部会话；运行中服务的旧 Cookie 因版本不符立即失效（不依赖进程内撤销），旧口令同时作废。凭据写入是条件写入，**攻击者并发发起的自助改密无法把这次强制重置覆盖回去**，只会自己拿到 `409 version_conflict`。若该账号仍有外部身份，可用 `--clear` 暂时关闭密码登录（「最后一种登录方式」的保护与清除在同一把身份锁内判定，与并发的解绑互斥）。
3. **不要用恢复旧备份来“撤销”泄露**。回滚数据库会把泄露的哈希与旧会话重新带回线上。凭据轮换是向前操作，恢复流程（§3）只在磁盘/数据损坏时使用。
4. **全库泄露时扩大轮换**。数据库导出同时包含 `oauth_accounts`、`settings` 与 `secret_ref` 指向的部署秘密，因此除全部本地密码外，还要轮换 OAuth client secret 等部署秘密材料，并按 §1 的秘密材料清单重新备份。
5. **核对运行记录**。用访问日志（`request_id`、method/path、status、耗时、已验证 `actor_id`）核对泄露窗口内的登录与写操作；日志**不含** Cookie、token 与请求正文，也不能凭它重建口令。本地密码失败限流是单实例内存计数、**重启即清零**，不构成持久审计；事件时间线必须另行留存。
6. **确认无残留**。核对受影响账号的角色与绑定未被篡改、没有新增未授权的 `oauth_accounts`、Owner 有效性与最后登录方式未被破坏。需要时按 §3 的隔离流程核对，但不要重放旧数据。
7. **防止二次泄露**。口令只经交互提示或 `--password-stdin` 传入，不得出现在命令行参数、脚本变量、CI 日志或工单文本；确认访问日志与错误响应不回显凭据（当前错误契约只回通用文案）。
