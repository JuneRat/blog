# 公开读取与混合负载容量验证

连接池参数可部署配置，参考[配置文档](configuration.md#连接池查询超时与数据库-tls)。当前默认仍是 5 个连接；不能把连接数直接当成 HTTP 并发数，查询完成后会归还连接。

## 查询路径和新鲜度

默认主题下，首页、成功的文章详情、独立 Page 各执行 3 次串行业务查询：内容、站点设置、主题选择。标签/分类/系列页增加目录对象查询，共 4 次；列表与总数在同一条 SQL 内。文章详情的正文、标签、分类和系列也在同一条 SQL 内。

这些是业务 SQL 调用数，不包含连接握手、SQLx 连接检查，也不适用于静态文件、404、feed/sitemap 或调用额外数据函数的自定义主题。主题函数有单次渲染内的查询缓存；站点设置、主题选择和整页没有跨请求缓存。

本轮先修复连接策略与来源限流并建立可重复测量，没有引入跨请求缓存。撤回、私密、删除的可见性仍在内容查询时判断，设置和已加载主题切换在后续请求生效。若真实流量显示设置查询占比较高，可合并读取 site/theme；这不必引入陈旧窗口。引入缓存则必须同时覆盖内容撤回、权限/可见性、设置修改和多进程失效测试。

## 重复运行

```sh
cargo build --release -p server --bin blog
pnpm --dir apps/admin build
# 指向专用的本地测试 PostgreSQL 管理连接；不要使用生产实例。
export BLOG_TEST_ADMIN_URL='postgres://test-user:password@127.0.0.1:5432/postgres'
python3 -B scripts/benchmark_public.py --report /tmp/blog-capacity.json
```

宿主机没有 PostgreSQL 工具时，额外设置 `BLOG_TEST_PG_CONTAINER` 为对应测试数据库容器名，工具通过容器执行管理命令。脚本只允许 loopback 管理地址，创建随机测试库、配置和媒体目录，退出时清理自己的资源；报告不覆盖已有文件，不包含连接凭据或安装码。

默认比较 5/10/20 个连接、1/8/32 个并发客户端，每组 1,000 个请求；各组令 min_connections 等于上限以预建连接，每次换池先重启并预热 30 次，不测冷启动成本。使用 release 版真实 HTTP 服务、默认主题、200 篇已发布文章和 1 个 Page，轮流请求首页/文章/Page，文章路径遍历样本中的文章，同时每 50 毫秒检查 `/readyz`。可用 `--pool-sizes`、`--concurrency`、`--requests` 调整客户端规模，`--posts` 调整文章数。

报告记录实际完成的读请求吞吐、P50/P95/P99、错误数、HTTP 状态分布、就绪检查延迟、二进制/脚本哈希和机器信息。格式 2 使用有界对数直方图，分位数为桶上界，误差不超过约 2% 加 1 微秒取整；长时间运行不保存逐请求样本。读取延迟计至响应体读完，与服务指标的响应头延迟不同。无样本的分位数为 `null`，不能解释为零延迟。

## 持续混合负载

在同一专用测试数据库中，`--mixed` 增加编辑客户端持续读取当前版本并保存已发布文章；`--writers` 指定客户端数量，每个客户端编辑独立文章。`--series-reorder` 把指定数量的样本加入同一系列，每个客户端每轮保存后反转完整成员顺序。单客户端内部串行，多客户端和公开读取并发，可形成系列重排与文章保存的版本及事务锁竞争。客户端各有独立 HTTP 状态，但沿用同一测试账号的会话；这不覆盖不同账号和角色的授权行为。

```sh
# 示例测试条件，不是生产容量承诺；每个连接池/并发组合各运行 60 秒。
python3 -B scripts/benchmark_public.py \
  --pool-sizes 5 10 --concurrency 8 32 \
  --posts 10000 --duration 60 \
  --mixed --writers 4 --series-reorder --series-members 1000 \
  --write-interval-ms 250 \
  --report /tmp/blog-mixed-capacity.json
```

| 参数 | 语义与边界 |
|---|---|
| `--posts` | 已发布文章数，1–100,000，默认 200；Page 固定 1 篇，正文沿用相同样本 |
| `--duration` | 每组运行 1–3,600 秒，替代固定读请求数量；已发出的操作允许完成，实际耗时可能略长 |
| `--mixed` | 开启作者保存；省略时仍为原有只读比较 |
| `--writers` | 独立编辑客户端数，默认 1，范围 1–32 且不超过文章数；需 `--mixed` 才运行 |
| `--series-reorder` | 每个客户端每轮另执行一次共享系列重排，要求 `--mixed` |
| `--series-members` | 共享系列成员数，默认 2，至少 2 且不超过文章数；仅影响启用的重排场景 |
| `--write-interval-ms` | 完成一轮保存/重排后暂停 10–60,000 毫秒，默认 250；不保证固定写入速率 |

每组的 `writes.save`、`writes.series_reorder` 分别汇总所有客户端的操作数、P50/P95/P99、`errors` 和 `conflicts`。写操作耗时包含获取当前版本/成员列表和提交的完整周期，不能当成单次 PATCH 耗时。重排从系列目录读取目标版本，再读取成员列表并提交完整排列。409 单列为 `conflicts`，其他非 200 结果计入 `errors`；`failed_operations` 为二者之和。冲突不会自动重试或计为成功，验收方须另行评估可接受冲突率。`error_types` 保留 HTTP 状态、传输/契约校验或客户端异常类型，不记录异常消息、响应正文或凭据。每次保存提交新的正文并核对返回版本，重排核对完整返回顺序。固定少量请求的 smoke 也至少让每个客户端执行一轮操作。

所有模式沿用随机测试库、隔离配置与归属检查，仅删除本次创建的资源；报告不覆盖已有文件。初始文章和系列关系为批量 SQL 构造的容量样本，测量中的保存与重排全部走 HTTP 业务事务。工具在读取/readiness 无失败、作者操作无非 409 错误且资源清理成功时返回 0；正常 CAS 冲突不会被误判为系统故障。即使全是写冲突，报告仍只说明未出现系统错误，必须查看成功操作数与冲突率。`passed` 不表示生产吞吐、延迟、冲突率或 RPO/RTO 门槛已达标。

比较时停止其他构建/压测。客户端、应用与数据库共用开发机，这些数据包含客户端开销和本地容器网络成本。客户端按“完成一个请求再发下一个”运行，不能证明固定外部到达率下的容量。即使使用混合模式，也没有覆盖公网延迟、真实正文分布、不同账号的权限变化、评论持续提交、预约任务积压、复杂主题或所有生产数据库资源竞争。上线前按[验收模板](release-acceptance-template.md)确认目标规格、数据规模、负载分布、持续时间和通过阈值，并结合连接池、渲染指标、数据库慢查询及客户端 CPU 分析结果。

## 故障验证

回归测试另外主动占满业务池，验证 `/readyz` 返回 503、`/livez` 仍为 200、释放连接后就绪恢复。语句和锁超时在 PostgreSQL 服务端执行；超时后的连接仍可用，超时终止的空闲事务连接会被替换。readiness 检查业务池可用性，不能用作进程自动重启依据。

## 2026-09-28 本地结果

[原始报告](validation/public-capacity-2026-09-28.json)：release 构建，macOS-27.0-arm64-arm-64bit，10 个逻辑 CPU；PostgreSQL 18 Alpine 运行于本机 Docker，启用数据库 TLS。每组 20,000 次，共 180,000 次页面请求及 1824 次就绪检查，均无错误。

32 个并发客户端时：

| 池上限 | 页面请求/秒 | 页面 P95 | 页面 P99 | readyz P95 |
|---:|---:|---:|---:|---:|
| 5 | 2454 | 15.03 ms | 16.22 ms | 5.58 ms |
| 10 | 3066 | 12.15 ms | 13.25 ms | 4.58 ms |
| 20 | 3928 | 9.74 ms | 10.65 ms | 3.88 ms |

这组负载显示扩大池可改善并发吞吐和延迟，5 个连接下也未出现就绪失败。保持默认 5 以兼容现有数据库预算，部署可按资源设置更大值；本轮不引入跨请求缓存。此历史报告采用格式 1、单个文章路径和精确样本分位数；新增的格式 2 遍历文章样本并支持混合负载，两者须记录条件后比较。历史结果没有测量持续后台写入、长事务或网络故障下的生产上限，目标环境验证仍待执行。
