# 公开读取与混合负载容量验证

连接池参数可部署配置，参考[配置文档](configuration.md#连接池查询超时与数据库-tls)。当前默认仍是 5 个连接；不能把连接数直接当成 HTTP 并发数，查询完成后会归还连接。

## 查询路径和新鲜度

默认主题下，首页、成功的文章详情、独立 Page 各执行 3 次串行业务查询：内容、站点设置、主题选择。标签/分类/系列页增加目录对象查询，共 4 次；列表与总数在同一条 SQL 内。文章详情的正文、标签、分类和系列也在同一条 SQL 内。

这些是业务 SQL 调用数，不包含连接握手、SQLx 连接检查，也不适用于静态文件、404、feed/sitemap 或调用额外数据函数的自定义主题。主题函数有单次渲染内的查询缓存；站点设置、主题选择和整页没有跨请求缓存。

本轮先修复连接策略与来源限流并建立可重复测量，没有引入跨请求缓存。撤回、私密、删除的可见性仍在内容查询时判断，设置和已加载主题切换在后续请求生效。若真实流量显示设置查询占比较高，可合并读取 site/theme；这不必引入陈旧窗口。引入缓存则必须同时覆盖内容撤回、权限/可见性、设置修改和多进程失效测试。

## 重复运行

```sh
cargo build --release -p server --bin blog
pnpm --dir apps/admin build
# 指向专用的本地测试 PostgreSQL 管理连接；不要使用生产实例。
export BLOG_TEST_ADMIN_URL='postgres://test-user:password@127.0.0.1:5432/postgres'
python3 -B scripts/benchmark_public.py --report /tmp/blog-capacity.json
```

宿主机没有 PostgreSQL 工具时，额外设置 `BLOG_TEST_PG_CONTAINER` 为对应测试数据库容器名，工具通过容器执行管理命令。脚本只允许 loopback 管理地址，创建随机测试库、配置和媒体目录，退出时清理自己的资源；报告不覆盖已有文件，不包含连接凭据或安装码。

默认比较 5/10/20 个连接、1/8/32 个并发客户端，每组 1,000 个请求；各组令 min_connections 等于上限以预建连接，每次换池先重启并预热 30 次，不测冷启动成本。使用 release 版真实 HTTP 服务、默认主题、200 篇已发布文章和 1 个 Page，轮流请求首页/文章/Page，文章路径遍历样本中的文章，同时每 50 毫秒检查 `/readyz`。可用 `--pool-sizes`、`--concurrency`、`--requests` 调整客户端规模，`--posts` 调整文章数。

报告记录实际完成的读请求吞吐、P50/P95/P99、错误数、HTTP 状态分布、就绪检查延迟、二进制/脚本哈希和机器信息。读请求和就绪探针默认每 60 秒主动轮换长连接，`--connection-lifetime-seconds` 可调整；报告分别记录轮换次数，计划轮换计入客户端耗时。服务默认连接寿命为 300 秒，持续测试不应让客户端固定连接跨过此边界；失败请求仍计入错误且不重试。格式 2 使用有界对数直方图，分位数为桶上界，误差不超过约 2% 加 1 微秒取整；长时间运行不保存逐请求样本。读取延迟计至响应体读完，与服务指标的响应头延迟不同。无样本的分位数为 `null`，不能解释为零延迟。

## 持续混合负载

在同一专用测试数据库中，`--mixed` 增加编辑客户端持续读取当前版本并保存已发布文章；`--writers` 指定客户端数量，每个客户端编辑独立文章。`--series-reorder` 把指定数量的样本加入同一系列，每个客户端每轮保存后反转完整成员顺序。单客户端内部串行，多客户端和公开读取并发，可形成系列重排与文章保存的版本及事务锁竞争。客户端各有独立 HTTP 状态，但沿用同一测试账号的会话；这不覆盖不同账号和角色的授权行为。

```sh
# 示例测试条件，不是生产容量承诺；每个连接池/并发组合各运行 60 秒。
python3 -B scripts/benchmark_public.py \
  --pool-sizes 5 10 --concurrency 8 32 \
  --posts 10000 --duration 60 \
  --mixed --writers 4 --series-reorder --series-members 1000 \
  --write-interval-ms 250 \
  --report /tmp/blog-mixed-capacity.json
```

| 参数 | 语义与边界 |
|---|---|
| `--posts` | 已发布文章数，1–100,000，默认 200；Page 固定 1 篇，正文沿用相同样本 |
| `--duration` | 每组运行 1–3,600 秒，替代固定读请求数量；已发出的操作允许完成，实际耗时可能略长 |
| `--mixed` | 开启作者保存；省略时仍为原有只读比较 |
| `--writers` | 独立编辑客户端数，默认 1，范围 1–32 且不超过文章数；需 `--mixed` 才运行 |
| `--series-reorder` | 每个客户端每轮另执行一次共享系列重排，要求 `--mixed` |
| `--series-members` | 共享系列成员数，默认 2，至少 2 且不超过文章数；仅影响启用的重排场景 |
| `--write-interval-ms` | 完成一轮保存/重排后暂停 10–60,000 毫秒，默认 250；不保证固定写入速率 |

每组的 `writes.save`、`writes.series_reorder` 分别汇总所有客户端的操作数、P50/P95/P99、`errors` 和 `conflicts`。写操作耗时包含获取当前版本/成员列表和提交的完整周期，不能当成单次 PATCH 耗时。重排从系列目录读取目标版本，再读取成员列表并提交完整排列。409 单列为 `conflicts`，其他非 200 结果计入 `errors`；`failed_operations` 为二者之和。冲突不会自动重试或计为成功，验收方须另行评估可接受冲突率。`error_types` 保留 HTTP 状态、传输/契约校验或客户端异常类型，不记录异常消息、响应正文或凭据。每次保存提交新的正文并核对返回版本，重排核对完整返回顺序。固定少量请求的 smoke 也至少让每个客户端执行一轮操作。

所有模式沿用随机测试库、隔离配置与归属检查，仅删除本次创建的资源；报告不覆盖已有文件。初始文章和系列关系为批量 SQL 构造的容量样本，测量中的保存与重排全部走 HTTP 业务事务。工具在读取/readiness 无失败、作者操作无非 409 错误且资源清理成功时返回 0；正常 CAS 冲突不会被误判为系统故障。即使全是写冲突，报告仍只说明未出现系统错误，必须查看成功操作数与冲突率。`passed` 不表示生产吞吐、延迟、冲突率或 RPO/RTO 门槛已达标。

比较时停止其他构建/压测。客户端、应用与数据库共用开发机，这些数据包含客户端开销和本地容器网络成本。客户端按“完成一个请求再发下一个”运行，不能证明固定外部到达率下的容量。`benchmark_public.py` 没有覆盖后台任务；下方 Compose 工具增加任务竞争。两者仍未覆盖公网延迟、真实正文分布、不同账号的权限变化、评论持续提交、复杂主题或所有生产数据库资源竞争。上线前按[验收模板](release-acceptance-template.md)确认目标规格、数据规模、负载分布、持续时间和通过阈值，并结合连接池、渲染指标、数据库慢查询及客户端 CPU 分析结果。

## Docker 后台任务对照压测

`benchmark_tasks.py` 使用已构建的运行镜像与仓库固定的 PostgreSQL 镜像，为每个池大小分别创建两套随机 Compose 项目：阅读＋编辑，以及阅读＋编辑＋后台任务。应用和数据库均在容器内运行；工具不复用现有 Compose 项目或数据库。镜像必须已存在本机，退出时删除本次创建的容器、卷和网络，报告以独占创建方式保存。安装凭据和子进程输出不进入报告。

```sh
docker build --build-arg VCS_REF="$(git rev-parse HEAD)" -t blog:task-capacity .
python3 -B scripts/benchmark_tasks.py \
  --image blog:task-capacity --expected-revision "$(git rev-parse HEAD)" \
  --pool-sizes 5 10 --posts 2000 --writers 4 --concurrency 16 \
  --duration 300 --task-interval 15 --scheduled-per-cycle 16 \
  --report /tmp/blog-task-capacity.json
```

每组先预热 30 次，读请求和编辑沿用上方真实 HTTP 与有界直方图。后台组每 15 秒在没有活动重建时将样本文章的派生版本标记为待重建，创建 100 条已过期评论 IP、100 条已过期审计记录，以及 16 篇五秒后到期的预约文章。活动重建期间继续提交请求并合并，跳过重复标记，避免把已经处理的样本再次变旧；报告记录跳过标记的周期数。过期评论采用正常 HTTP 种子评论的当前渲染版本。夹具通过 SQL 构造，测量中的编辑、一次性 HTML 计划和立即清理请求全部经过 HTTP；预约发布由正常的 30 秒周期调度执行，不提前推进其时钟。周期到期前的主动等待不算执行耗时。同类请求可能合并到已有任务，报告保留不同请求数和唯一执行数。对照组仍运行空闲的预约发布检查。

报告记录每组页面和完整保存周期的 P50/P95/P99、吞吐、就绪检查与错误／冲突数，任务请求响应时间、每次执行的到期等待和耗时、实际重建报告、清理剩余数，以及预约发布的最大／P95 延误。编辑客户端共用测试账号、分别编辑不同文章，409 单列；全部保存都冲突不能判定通过。后台任务在读负载停止后继续等待已接收工作完成，排空时间不计入页面吞吐；仍要求重建和清理各有一次在持续读写窗口内确认完成。清理另外核对评论行数、源文和新 IP 保留，避免把误删内容当成成功。

发布延误以每五秒首次观测到数据库行已发布的时间减去预约时间，包含领取、锁与提交等待，是实际数据库可见延迟的观测上界，另保存业务 `updated_at` 延误。观测记录写入本次随机库的独立夹具表，不进入应用迁移或指标标签；最后排空后再观测全部已发布样本。报告同时保留夹具 SQL 耗时；后台组增加了夹具生成、发布观测与持续增长的数据量，A/B 结果描述这些负载下的共存，不能把全部差异只归因于任务执行器。样本源文相同，大量重建会命中 Markdown 缓存，不能推断不同复杂正文的纯渲染 CPU 上限。

每五秒采集独立指标端口的连接池、渲染与任务指标，以及两个容器的内存和 CPU；结束排空后额外采样一次。报告保留指标的首／末／最小／最大值和容器资源峰值。采样频率无法捕捉所有短峰；CPU 为 Docker 相对单核的百分比。记录镜像 ID、架构、编译提交、机器信息和脚本哈希，方便比较同条件结果。

默认的本地回归门槛为页面 P95 ≤500ms、完整保存周期 P95 ≤2000ms、预约最大观测延误 ≤45s；参数 `--read-p95-ms`、`--write-p95-ms`、`--publication-delay-seconds` 可调整，必须在执行前确定。还要求读取／就绪无失败、编辑无非 409 错误且有成功保存、结束时调度器健康且采样期间未新增调度错误、后台任务全部成功且实际完成重建／清理／预约发布、最终待重建数量为零、监控采样与资源清理成功。单个 HTML 请求共享 10,000 行的预算；扩大文章规模后若留有余量，此工具判为未通过，须另行安排多轮全量重建验收。默认 5/10 连接各两组、每组 300 秒，共约 20 分钟加安装与排空。失败组保留前台结果、可取得的后台业务报告和 `failed_checks`，不会因后台校验失败丢弃整组证据。通过只代表上述条件下的本地门槛，不定义生产 SLA、RPO/RTO 或资源上限；长事务、故障注入与部署目标的持续负载须分别验收。

任务终态历史每类最多保留 500 条，工具核对唯一请求数量与取回的执行记录，历史被裁剪时判为证据不完整。长时高频测试应缩短单轮时长或增大任务间隔，不能仅凭保留下来的成功记录通过。

## 2026-10-01 Docker 任务共存结果

[原始报告](validation/task-capacity-2026-10-01.json)四组均通过预设门槛。运行镜像来自干净提交 `9057c1c`，Linux arm64；宿主机 macOS 27、10 个逻辑 CPU。每组 2,000 篇初始文章、1 个 Page、16 个读取客户端、4 个编辑客户端，持续 300 秒，正文相同、默认主题、池内预建全部连接。客户端每 60 秒轮换连接，各组实际记录 64 次读取连接轮换和 4 次就绪连接轮换。

| 池上限 | 后台负载 | 页面请求/秒 | 页面 P95 / P99 | 完整保存 P95 / P99 | 应用 / 数据库内存峰值 |
|---:|---|---:|---|---|---|
| 5 | 读写基线 | 5584.88 | 4.230 / 5.472 ms | 24.164 / 39.644 ms | 79.20 / 87.90 MiB |
| 5 | 重建＋清理＋预约发布 | 4579.39 | 5.365 / 7.079 ms | 29.456 / 77.728 ms | 73.82 / 98.22 MiB |
| 10 | 读写基线 | 4486.27 | 5.472 / 7.079 ms | 35.202 / 57.753 ms | 71.21 / 99.98 MiB |
| 10 | 重建＋清理＋预约发布 | 5776.27 | 4.066 / 5.055 ms | 25.140 / 38.104 ms | 68.89 / 124.90 MiB |

合计 6,128,131 次读取、17,503 次成功保存，读取／就绪／保存错误及 CAS 冲突均为 0。每个后台组各有 20 次 HTML 重建和 20 次清理成功，其中每类各 19 次在持续读写窗口内完成，末轮在排空阶段完成；最终 Post/Page/comment 待重建数均为 0。各组清理 2,000 条过期 IP 和 2,000 条过期审计夹具，保留全部评论源文及种子评论的新 IP。

两个后台组各发布并实际观测到 320 篇预约文章，最大观测延误分别为 26.026／26.064 秒，P95 为 26.007／26.043 秒，均低于运行前设定的 45 秒门槛。它们是每五秒观测的数据库可见上界，正常发布调度周期为 30 秒。全部监控采样成功，结束时调度器健康且没有新增调度错误；容器 CPU 峰值和连接池采样保留在原始报告。

四组顺序运行、没有重复随机化，结果包含开发机与客户端的波动；10 连接后台组比基线更快不能解释为后台任务提高性能，也不能据此认定 10 连接优于 5。保持默认池大小 5，部署规格变化后按相同条件复测。首轮失败、客户端和夹具修正、测量后增加的历史完整性守卫、镜像身份及[资源清理结果](validation/task-resources-2026-10-01.json)见[完整验收记录](validation/task-validation-2026-10-01.md)。

## 故障验证

回归测试另外主动占满业务池，验证 `/readyz` 返回 503、`/livez` 仍为 200、释放连接后就绪恢复。语句和锁超时在 PostgreSQL 服务端执行；超时后的连接仍可用，超时终止的空闲事务连接会被替换。readiness 检查业务池可用性，不能用作进程自动重启依据。

## 2026-09-28 本地结果

[原始报告](validation/public-capacity-2026-09-28.json)：release 构建，macOS-27.0-arm64-arm-64bit，10 个逻辑 CPU；PostgreSQL 18 Alpine 运行于本机 Docker，启用数据库 TLS。每组 20,000 次，共 180,000 次页面请求及 1824 次就绪检查，均无错误。

32 个并发客户端时：

| 池上限 | 页面请求/秒 | 页面 P95 | 页面 P99 | readyz P95 |
|---:|---:|---:|---:|---:|
| 5 | 2454 | 15.03 ms | 16.22 ms | 5.58 ms |
| 10 | 3066 | 12.15 ms | 13.25 ms | 4.58 ms |
| 20 | 3928 | 9.74 ms | 10.65 ms | 3.88 ms |

这组负载显示扩大池可改善并发吞吐和延迟，5 个连接下也未出现就绪失败。保持默认 5 以兼容现有数据库预算，部署可按资源设置更大值；本轮不引入跨请求缓存。此历史报告采用格式 1、单个文章路径和精确样本分位数；新增的格式 2 遍历文章样本并支持混合负载，两者须记录条件后比较。历史结果没有测量持续后台写入、长事务或网络故障下的生产上限，目标环境验证仍待执行。
