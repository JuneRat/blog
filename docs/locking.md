# PostgreSQL 锁协议

所有业务 advisory 键在 `crates/infrastructure/src/locks.rs` 注册，二元组共享一个跨进程名字空间。新增键须保持唯一，并更新下表和相应并发测试；禁止按模块自行复用数字。

| 键 | 职责 | 模式与获取顺序 |
|---|---|---|
| `(2048001, 1)` | 身份、权限、登录方式保留与业务写授权 | 身份变更取排他锁，已认证业务写入取共享锁；先身份锁并复核账号认证版本与权限，再业务锁/用户与角色事实和关联修改，最后会话撤销、审计；持有至提交或回滚 |
| `(2048002, 1)` | 会话容量、批量撤销 | 排他；先会话锁，再过期/淘汰会话行，最后插入会话取得用户外键 KEY SHARE |
| `(2048004, 1)` | 主题选择、配置与包生命周期 | 排他；先主题操作锁，再主题记录/选择行，再媒体引用 SHARE 行锁，最后审计；发布目录及补偿由文件租约和持久化日志保护 |
| `(2048003, 1)` | 分类树无环、删除保护 | 排他；先树锁，再分类事实与写入 |
| `(1129270868, 1)` | 内容关系、系列成员与版本；正文插件版本与媒体清理协调 | 内容关系/插件设置写入取排他锁，媒体物理清理取共享锁；均先取得此锁，再取得插件运行记录、插件配置/媒体等行锁，最后写审计 |
| `(1129270605, 1)` | 评论全局策略 | 提交取共享锁，策略变更取排他锁；再文章行、评论父链/评论行 |
| `(1129270605, 2)` | 审计保留策略 | 与评论策略同时读写时，总是先评论策略锁再审计策略锁 |
| `(1129270605, 3)` | 保留期清理单执行者 | 先清理锁，再共享评论策略锁、共享审计策略锁，最后分批处理记录 |

SQLx 的迁移锁由 SQLx 管理，使用独立的单 bigint 键空间。

这是实际会嵌套的锁序约束；不要求每个事务取得整张表中所有锁。身份与会话 advisory 协议互相独立，不能在持有会话行时再反向取得身份锁。新增跨协议操作必须审查它与现有路径形成的完整等待图。

已认证写事务统一经 `begin_authorized_write` 取得共享身份锁并读取最新身份事实，使用 READ COMMITTED；已有身份变更事务先取排他身份锁，再调用 `revalidate_write`。禁止先共享再升级排他，也不能先取得文章、用户、媒体、任务或其他业务锁再申请身份锁。安装引导、游客提交和已授权入队后的系统任务不携带请求身份快照；任务审计仍保留原操作者。升级时必须停止旧版写进程后整体替换，旧程序不会参与新增的共享锁协议。

系列重排先锁系列行，再按文章 ID 升序锁成员；文章保存先锁文章行，再按系列 ID 升序锁受影响的系列。这两种行锁顺序由预先取得的全局内容关系锁串行化；禁止绕过该锁或取得行锁后才补取。若将全局锁改为按资源加锁，必须重新设计并验证这些路径的统一行锁顺序。

用户认证修订、密码和身份绑定不修改外键身份：显式用户行锁必须用 `FOR NO KEY UPDATE`，不能用 `FOR UPDATE` 阻塞会话插入的 KEY SHARE。清除密码与绑定外部身份都在修改用户后删除会话；过强用户锁会与“会话淘汰后插入”形成反向等待。普通非键 UPDATE 同样兼容 KEY SHARE。真正删除或修改用户主键需要另行设计协议，不能机械替换锁。

所有锁都随事务结束释放。HTML 渲染、大文件写入和外部 HTTP 不得放到这些数据库锁内。主题生命周期是短操作例外：预检、解压和文件 fsync 在事务外完成，持有主题锁时仅写小型操作日志、原子 rename 和目录 fsync，以便目录隔离与数据库决定保持顺序。正常服务还持有主题根目录的文件租约，避免其他服务进程保留过时注册表；此锁不参与媒体物理清理等待图。系列重排先锁定完整成员集合，再批量改关系和文章版本；仅改变位置的成员写审计，无变化不递增版本。评论资源授权调用应用策略，但归属事实必须保持到提交，不能将授权检查简单移出事务。

此次分类树锁从历史上与会话冲突的 `(2048002, 1)` 改为 `(2048003, 1)`。升级时停止旧 server/CLI 写入进程，再启动新版本；不要混跑不同锁协议版本。当前 Compose 单实例整体替换符合这一要求。

注册和参与设置使用 `ACCESS_POLICY (1129270605, 4)`：修改开关取排他锁，注册及游客评论提交取共享锁后复核开关。注册按排他 IDENTITY → ACCESS_POLICY 获取，已认证设置更新按共享 IDENTITY → ACCESS_POLICY 获取；游客评论按 COMMENT_POLICY → ACCESS_POLICY → 文章/用户行锁获取。已认证评论先取得共享 IDENTITY，再沿用评论策略与业务行锁顺序。

评论审核策略和全站开关共享 COMMENT_POLICY 锁与设置组版本。首次评论审核在文章/父评论事实之后，读取仍为 approved 的人工通过记录并取 FOR SHARE，保持该记录到提交结束；人工撤回通过状态取评论行的 FOR UPDATE，因此二者按取得锁的顺序生效。自动通过的记录不参与资格查询。

事务性批量文章操作先取得 CONTENT_RELATIONS 排他锁，再按文章 ID 升序取得全部目标行锁；分类变更在同事务内持有目标分类 KEY SHARE，永久删除在内容锁内更新系列版本并清理整棵评论树和媒体引用。批量评论审核先取得 COMMENT_POLICY 排他锁，再按文章 ID 升序取得 SHARE、按评论 ID 升序取得 UPDATE，核验全部版本与归属后提交。排他策略锁使多评论审核与提交使用的父链/跨文章人工通过记录锁互斥，避免多目标锁与首次评论判定形成反向等待；已有单条审核路径保持原有锁协议。批量请求最多 100 项，不在锁内渲染正文或执行外部 HTTP。
