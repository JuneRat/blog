## 场景与预设门槛

每组初始 2,000 篇公开文章、1 个 Page，16 个读客户端轮流访问首页／文章／Page，4 个作者共用同一测试账号会话，各自编辑不同文章。连接池预建全部 5 或 10 个连接；先预热 30 次，正式持续 300 秒，读连接每 60 秒轮换。每次写作循环结束后等待 250 ms。

写作循环通过真实 HTTP 获取版本、保存修改草稿、匿名读取确认草稿未公开且前次发布仍可见、显式发布、确认新正文公开、读取历史列表与此次发布的历史正文。每轮正文有不同标记。完整循环含 7 次 HTTP 请求；`writing.phases` 将五个阶段分别计时，`writes.save` 保存完整循环耗时，格式 2 的该字段不能与旧格式的单次保存周期直接比较。

负载及任务排空后，每个作者再保存一个未发布修改，验证后台可读、公开正文未变，并直接查询物理历史行数。要求实际只保留 50 份历史、旧版本被裁剪、活跃草稿引用仍存在；不以 API 列表的 50 条返回上限推定裁剪成功。最终 16 次草稿保存及数据库核验不计入写作延迟。

| 检查 | 执行前门槛 |
|---|---|
| 页面读取 | P95 ≤500 ms，读取与就绪无失败 |
| 完整写作循环 | P95 ≤2,000 ms，各阶段无非 409 错误，每个作者至少 30 个完整成功循环；CAS 冲突单列且不重试 |
| 草稿和历史 | 保存不公开，显式发布可见，历史正文一致，数据库实际裁剪及活跃草稿完整性通过 |
| 预约发布 | 最大数据库可见观测延误 ≤45 秒，全部样本发布并被观测到 |
| 后台与清理 | 已接收任务全成功，重建／清理均在读写窗口内有完成记录，最终重建积压为零；监控无错误、调度器健康、无新增调度错误、资源清理成功 |

## 后台工作与数据核验

每轮通过 SQL 构造容量夹具并以 HTTP 提交重建／清理，提交完成后等待 15 秒再开始下一轮；正式组各完成 19 轮。每轮创建 100 条过期评论 IP、100 条过期审计和 16 篇五秒后到期的预约文章。预约发布沿用真实 30 秒调度周期。重建仍在执行时不重复把已处理文章标旧，请求可以合并；5/10 连接组分别跳过 9/11 次重复标记。

两组共发布 608 篇预约文章；各组均清理全部 1,900 条过期 IP 和 1,900 条过期审计夹具，保留 1,900 条评论源文和种子评论的新 IP。所有请求对应的唯一执行记录完整且成功，最终 Post/Page/comment 待重建数量均为零。最后一次重建在前台停止后的排空期间完成，不计入页面吞吐。单次重建最长分别为 19.190 / 59.345 秒，任务合并后仍有完整执行证据。

发布延误是每五秒观测数据库已发布状态得到的上界，包含实际领取、锁、提交等待与观测开销；不是业务 `updated_at` 的差值。夹具 SQL 也构成额外负载，其 P95 分别为 1.126 / 2.800 秒，原始报告单独记录，不能将全部组间差异归因于应用任务执行器。

## 复现与边界

```sh
python3 -B scripts/benchmark_tasks.py \
  --image codex-blog-release:9fb6c2425fa5 \
  --expected-revision 9fb6c2425fa5dea132faa9e52bf061054a312788 \
  --pool-sizes 5 10 --posts 2000 --writers 4 --concurrency 16 \
  --duration 300 --task-interval 15 --scheduled-per-cycle 16 \
  --report /tmp/blog-writing-capacity-new-run.json
```

这是本地回归通过证据，不代表生产 SLA、资源上限或 RPO/RTO。与 2026-10-01 的报告相比，应用加入身份锁与修订写入，工具也增加了发布、可见性和历史请求，因此没有给出跨版本性能提升／退化比例。客户端、应用和数据库共用开发机，客户端按完成后再发下一请求的方式工作；种子文章正文重复，后台重建可命中渲染缓存。

本轮没有并发修改同一正文、撤权或共享系列重排负载，零 CAS 冲突不能证明这些场景没有竞争；持续系列重排仍待独立测量。复杂正文与主题、不同账号、媒体持续上传、公网延迟、限额机器、固定外部请求到达率和故障注入仍需目标环境证据。真实 SMTP 送达与预发布部署继续按[路线图 M5](../product-roadmap.md#3-里程碑与验收入口)验收。
