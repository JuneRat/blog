# 插件、多数据库与外部集成

状态：后续扩展设计草案。当前先实现 [13 表核心](database-design.md)，本文的 outbox、任务和外部投递在 M4 对应能力交付时追加存储。已确认仅 PostgreSQL，预留多数据库；插件采用主题、Webhook、外部服务适配等受限扩展点，搜索/统计提供商待确认。

## 1. 扩展边界

三种能力分别设计，不能全部塞进通用插件运行时：

| 能力 | 扩展机制 | 示例 |
|---|---|---|
| 展示 | MiniJinja 主题、模板数据契约和宿主只读函数 | 页面布局、样式、受控数据查询 |
| 外部服务 | application 端口 + infrastructure 适配器 | 搜索、统计、邮件、对象存储 |
| 插件 | 版本化扩展协议与授权能力 | 订阅发布事件、内容转换、后台扩展 |

模板数据函数是核心宿主提供的受限 API，具体见 [主题与渲染](themes-and-rendering.md)，不等于允许主题提供执行代码。

内置搜索提供商可以先通过编译期适配器接入，无须等待代码插件运行时完成。插件也不能绕过应用用例直接操作核心数据库。

## 2. 首期受限扩展

首期交付主题包、Webhook 订阅和内置外部服务连接，不提供通用可执行插件安装器。主题由独立清单与激活流程管理；Webhook/连接配置不必套用完整代码插件包协议。

连接配置建议包含 ID、provider、启用状态、设置 Schema 版本、非敏感参数、secret 引用及健康状态；Webhook 增加事件订阅、目标、签名密钥引用和投递策略。生命周期为创建 → 配置/测试 → 启用 → 暂停/禁用 → 删除。删除前明确投递记录与历史配置的保留规则。

服务适配器随可信应用发布构建，管理员只能配置已安装的 provider，不能上传 Rust/WASM/JavaScript。新的 provider 仍通过 application 端口实现；读取、配置、启停和投递重放使用独立 RBAC 权限，并记录审计。

首批扩展点：提交后的内容事件 Webhook、搜索适配、统计接入和声明式设置页。认证判定、核心事务、任意 SQL、同步内容修改钩子不开放。普通连接配置归 site 应用设置，凭据由基础设施秘密存储管理，不预建 ExtensionInstallation 聚合。

主题包需要路径、大小、文件类型、版本和完整性检查；适配器配置没有包时，不强行要求安装入口、包签名或插件 KV。管理员配置的出站目标仍需校验地址、DNS 结果和重定向，限制内部网络访问；确需私有服务时采用部署白名单。目标测试也受相同限制。

事件投递仅提供必要字段；服务主体使用显式能力，不继承配置者的 Owner 权限。第三方脚本不直接注入后台同源 SPA。首期后台设置通过声明式表单呈现。

### 后续演进，非首期要求

可信 Rust 编译期扩展与 WASM 运行时都是未来方案；没有通用代码运行时也不影响首期“受限扩展”的交付。真正引入第三方代码时再设计版本化 SDK、包清单、能力授权、命名空间存储、迁移/回滚和隔离 UI。

WASM 可以评估 Wasmtime/WIT，不以 Rust 动态库 ABI 作为默认插件接口。运行时必须限制 CPU、内存、并发、输出和 I/O；沙箱不能代替宿主 API 授权。声明式扩展若出现独立业务生命周期，也可先提取聚合，不必等到代码插件时代。[Wasmtime 安全模型](https://docs.wasmtime.dev/security.html)

## 3. 多数据库

多数据库默认指“一次部署选择一种关系数据库”，不表示跨库分布式事务、同时写入多种数据库或在线无缝切换。已确定首期只支持 PostgreSQL；SQLite/MySQL 是后续适配候选，不创建空驱动、空 feature 或宣称当前可切换。

```text
crates/infrastructure/src/persistence/
├── postgres/
├── sqlite/           # 后续适配规划
└── mysql/            # 后续适配规划
migrations/
├── postgres/
├── sqlite/           # 后续适配规划
└── mysql/            # 后续适配规划
```

首期 server 只装配 PostgreSQL。真正增加第二种数据库时，再由 Cargo feature 控制打包哪些驱动，启动配置选择已编译的后端。仓储与工作单元端口保持一致，各后端拥有自己的 SQL 和迁移。不把 SQLx Any 或统一 SQL 语法等同于业务语义兼容。以下兼容约束作为未来适配验收清单，首期只要求 PostgreSQL 对应部分。

核心表、字段和事务映射见 [数据库设计](database-design.md) 与 [DDL 草案](sql/postgres-core.sql)。部分索引、事务级 advisory lock、系列位置的延迟唯一约束及外键须在真实 PostgreSQL 中验证；媒体两表已随媒体库第一版交付，外部任务随功能补充 DDL。未来后端提供等价语义，不承诺直接复用同一份 DDL。

兼容约束：

- 使用应用生成的稳定 ID，统一时间精度和 UTC 表示，明确布尔值、JSON、NULL、排序规则与大小写语义。
- Slug 等唯一键使用应用定义的规范化形式，不依赖数据库默认 collation 达成一致。
- 外键、唯一约束、乐观锁和原子 outbox 写入必须在每个后端验证。
- SQLite 每个连接显式开启并验证外键；事务、busy timeout、写入并发和 WAL/备份方案独立设计。SQLite 面向单机部署，不作为共享网络文件上的多实例数据库。[SQLite 外键文档](https://www.sqlite.org/foreignkeys.html)
- worker 的任务领取采用各后端适合的原子租约实现，不能依赖全部数据库均支持相同的行锁语法。
- 检查数据库特有的 DDL 和事务限制；每个后端独立验证迁移失败恢复，不假设所有迁移可回滚。
- 搜索能力与关系数据库分离；不得把 PostgreSQL 特有全文搜索当作跨数据库基线。

迁移记录各后端 schema 版本。启动检测配置与 schema 兼容性；多进程升级需迁移互斥，备份后升级。SQLx 编译期查询校验与离线元数据按驱动组合验证，避免只在一个数据库上通过。

跨数据库迁移使用版本化逻辑导出/导入：先暂停写入，导出内容、身份关联、角色、配置及媒体清单，导入目标库后验证数量、关系和校验和，再切换。会话默认失效；密钥和第三方凭据通过独立安全流程迁移。无需首期承诺不停机迁移。

部署备份需同时覆盖数据库、媒体、主题与恢复所需密钥，不能用上述逻辑迁移清单替代完整备份。一致性切点、隔离恢复及 worker 重启规则由 [备份与恢复](operations-and-recovery.md) 统一定义。

“支持某数据库”的验收条件是共享仓储契约测试、用例集成测试、迁移升级、并发冲突、outbox 和备份恢复均通过，而不是驱动能连接。各后端的容量与性能单独报告。

## 4. 搜索服务

application 定义 `SearchQuery` 和 `SearchIndex` 等端口。公开搜索与后台搜索使用不同授权与索引范围；外部搜索服务不参与内容发布事务。

内容提交 → outbox → 索引任务 → 提供商适配器。内容变更事件建议采用以下契约，与业务写入同事务落库；这是 M4 的实现输入，不表示已创建事件表：

| 字段 | 含义 |
|---|---|
| event_id | 事件唯一身份，重试和手动重放沿用原值，用于去重 |
| stream_epoch | 本次事件流的恢复世代，隔离备份回退前后的版本序列；正常重启不变 |
| content_type + content_id | 被排序的内容身份，永久删除后不复用 ID |
| aggregate_version | 本次提交后的内容聚合版本，用于同一世代内同一内容的先后比较 |
| payload | 按事件契约保存的最小内容/状态快照；当前无 revision_id，不能依赖后续再读取旧正文 |
| event_type / schema_version | 变更语义和事件载荷格式版本，分别演进 |

正文即使没有变化，撤回和再次发布也必须增加 aggregate_version。例如发布 v10、撤回 v11、再次发布 v12，按 v12 → v10 → v11 到达时最终索引仍对应 v12。版本允许因未发公开事件的草稿保存而跳号；消费者不等待连续版本，也不按 UUID、时间戳或队列领取顺序推断提交顺序。同一内容每个提交版本只产生一份供索引处理的最终状态变更；不重新引入修订表作为事件前提。

消费水位按 `(stream_epoch, content_type, content_id)` 隔离。备份恢复后聚合版本可能回退，重新开放写入前创建新的 stream_epoch，并与需要维护状态的接收端核对新基线后才启用投递；不同世代的版本不可直接比较，未知世代也不能自动覆盖现有状态。旧事件重放保留原世代及事件 ID，旧世代的迟到请求不得修改新世代的读模型。此字段在 M4 事件协议落地，恢复流程见 [备份与恢复](operations-and-recovery.md)。

删除与取消发布使用携带版本的 tombstone。永久删除用比此前状态更高的版本写出删除事件，并保留独立于已删除聚合的消费水位/墓碑记录，避免级联清理后旧事件重新建索引。水位保留覆盖支持的重放范围；超出保留范围的事件拒绝直接重放，改走当前状态重建。

适配器使用提供商的版本条件写入，或能保证远端完成顺序的逐内容串行处理，拒绝旧版本、幂等处理相同版本。仅在请求发出前比较本地水位不够：并发旧请求、租约过期和远端超时后继续执行都可能覆盖新状态。推进水位前确认远端结果；无法判断的请求进入核对/重试状态，不宣称已成功。提供商选择时必须验证上述并发与超时语义。

索引消费者可以把积压事件合并为当前主库状态同步；内容、关系和版本来自同一一致性读取，只索引当前 public、published、未删除内容，不能用新版本号包装事件中的旧正文。本版不保留历史修订，事件若需原始内容必须在生产事件时冻结 payload。分类、标签、系列名称等独立可变元数据变更须触发相关文档重建，并采用覆盖这些变更的投影版本/顺序契约，不能只比较未改变的 Post.version；具体字段在选择提供商时固定并测试。

公开索引只包含公开内容。返回结果前根据主库当前可见性重新过滤，再构造标题、摘要及链接；不能仅过滤 ID 却把外部服务缓存的私有摘要继续返回。公开搜索建议经过后端代理，避免直接外部搜索泄漏已撤回内容。查询外发的数据范围与第三方保留策略必须在集成设置中说明。

支持全量重建、版本化索引切换、同步状态和失败重试。服务故障时公开文章仍可阅读；搜索明确提示暂不可用，或切换到已定义语义的基础检索，不能悄悄返回空结果冒充没有匹配。

具体引擎及中文分词需求待确认，按中文检索质量、运维成本、授权过滤与重建能力做样例验证后选择。

## 5. 统计与其他外部服务

统计区分访问事件采集和后台报表查询，分别定义端口。页面事件异步、有界发送；统计服务故障或配额耗尽不能阻塞正文。第三方脚本加载失败不影响阅读。

指标定义明确：PV、UV、时区、机器人过滤、延迟与保留周期。不把估算 UV 当作精确人数，不把访问日志与业务审计日志混为一体。事件默认不包含 token、Cookie、完整敏感查询参数或草稿内容；是否收集 IP、Cookie 及是否需要用户同意由部署策略明确。

报表 API 受 `analytics.read` 控制；凭据只在服务端。第三方嵌入报表需要提供商支持的访问约束，不能把私有报表公开链接作为权限方案。

邮件、对象存储和 Webhook 均走独立端口。Webhook 用 outbox 和投递记录驱动，内容事件沿用 §4 的事件身份及聚合版本，另带投递时间戳、签名和重试策略；接收端需去重，不能假设网络到达顺序等于内容变更顺序。用于重放的最小事件载荷与事件同事务保存，不依赖之后可能被清理的历史修订，也不把当前新正文冒充旧事件内容。提供死信与手动重放，重放保留原 event_id。不同服务使用不同重试预算；统计可以丢弃非关键事件，内容索引和业务通知不能无记录静默丢弃。恢复备份可能回退投递记录，重新开放投递遵循 [备份与恢复](operations-and-recovery.md)，不承诺仅靠恢复本地记录实现恰好一次外部投递。

## 6. 共用运行能力与验收

集成配置包含 provider、启用状态、非敏感参数、secret 引用、健康状态与最近错误。所有出站适配器配置超时、并发上限、重试/退避、限流和断路策略，日志脱敏；服务不可用不能导致整站重启循环。

任务先采用主库持久化队列/outbox worker，与 HTTP 生命周期分开管理，首期可同进程运行。任务类型声明幂等性、顺序要求、租约、重试上限与死信处理，未来再决定是否独立 worker 进程。

本扩展阶段验收包括：连接配置越权、禁用后停止新增投递、出站地址约束、外部服务停机、相同正文发布/撤回/再发布的乱序消费、永久删除后迟到旧事件、远端超时与租约重领竞态、正文后续修改后的事件重试、统计背压、Webhook 重复投递和保留事件 ID 的重放、备份恢复后旧投递隔离与不同世代水位分离、配置删除后的历史保留及 PostgreSQL 迁移恢复。代码插件崩溃隔离、其他数据库契约与跨库数据核对在对应能力交付时另行验收。
